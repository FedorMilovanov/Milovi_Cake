## Новый контролируемый опыт: нижеэкранный DOM главной

Воспроизводимый dev-only скрипт: [`scripts/diagnostics/home_dom_lcp.cjs`](../scripts/diagnostics/home_dom_lcp.cjs). На машине с `npm ci`, Playwright Chromium и OpenSSL:

```sh
node scripts/diagnostics/home_dom_lcp.cjs 8 full,hero,comment
node scripts/diagnostics/home_dom_lcp.cjs 8 full,contain
```

Только тестовый сервер: локальные HTTPS + gzip + **h2**, один HTML/одни CSS, новый browser context и отключённый cache на каждом запуске. 390×844, `isMobile`, DPR 2, light, reduced-motion, RTT 100 мс, 1600 Кбит/с, CPU ×1/×4; порядок вариантов циклически менялся. Google Fonts недоступны в sandbox: один и тот же **пустой CSS font mock** для всех вариантов. Выполняемые скрипты сайта удалены **в обоих сравниваемых ответах** (исходники в репозитории не менялись), чтобы отделить HTML/стили от runtime. Footer и мобильная панель остаются одинаковыми.

- `full`: вся главная без исполняемых скриптов — **144 685 HTML-байт / 32 797 gzip**, 1112 DOM-элементов.
- `hero`: нижеэкранные секции в `<main>` убраны только в памяти тестового сервера, footer сохранён — **82 279 / 19 562 gzip**, 479 элементов.
- `comment`: те же нижеэкранные секции вместо DOM находятся в HTML-комментарии; **144 748 / 32 822 gzip**, 479 элементов. Эта пара почти уравнивает время/размер передачи HTML и CSS при одинаковом первом экране.
- `contain`: полный DOM и HTML, тестовый CSS дополняется `#main-content > section:not(.hero) { contain: layout style; }`. Ничего из этого в production CSS не добавлено.

**Медианы 8 пар в каждом режиме** (ms; `delta` = вариант − `full`):

| CPU / вариант | FCP=LCP full → вариант | Парная delta | CSS responseEnd delta | LayoutDuration full → вариант* |
| --- | ---: | ---: | ---: | ---: |
| ×1 / `hero` | 906 → 810 | **−88**, 8/8 | −45,6 | 49,1 → 29,1 |
| ×1 / `comment` | 906 → 856 | **−50**, 8/8 | −1,2 | 49,1 → 28,2 |
| ×4 / `hero` | 1134 → 960 | **−162**, 8/8 | −21,9 | 178,4 → 100,9 |
| ×4 / `comment` | 1134 → 988 | **−142**, 8/8 | −0,2 | 178,4 → 103,3 |
| ×1 / `contain` | 888 → 880 | **−8**, 6/8 | −0,4 | 44,8 → 45,0 |
| ×4 / `contain` | 1156 → 1138 | **−12**, 5/8 (2 равны) | −0,3 | 192,9 → 182,5 |

\* `LayoutDuration` — накопленный CDP-счётчик после load + 850 мс, **не** точное время layout до LCP. В `comment` при ×4 `RecalcStyleDuration` уменьшился **88,3→36,0 мс**. У `hero` быстрее и передача HTML, поэтому его парная разница не изолирует именно стилизацию. У `comment` gzip отличается на **25 байт**, время CSS/HTML responseEnd в паре почти не менялось; это подтверждает измеримую цену нижеэкранных узлов **в локальном no-JS варианте**, не production-корень предупреждения.

В 48 `full/hero/comment` и 32 `full/contain` загрузках: h2=все, LCP-элемент `.hero-img`=все, `naturalWidth=640`, применён весь CSS, CLS=0, JS/локальных сетевых ошибок=0. Первые viewport PNG (`full/hero/comment`; также `full/contain`) имели **pixel AE=0**. Скрипт сохраняет сырые JSON и PNG в ignored `_review_screens/`; при пересоздании песочницы они могут пропасть, поэтому здесь оставлены условия и числа. `contain` сохраняет доступный DOM, но его **8–12 мс** локального эффекта при смешанных знаках и потенциальных изменениях layout недостаточно для production-патча.

При CPU×4 по очереди превращали **одну** текстовую секцию в HTML-комментарий: весь ответ передавался, но её узлы не создавались. Восемь пар для двух крупнейших секций; картинки первого экрана побайтно совпали, CSS завершался примерно одновременно, все 32 загрузки: h2, hero `naturalWidth=640`, CLS=0, ошибок=0. Контроль `comment` убирает все секции ниже hero. Разницы между режимами **не складываются**.

| Тестовый режим | DOM-узлов / gzip HTML | Медиана парной LCP (режим − `full`) | Знак |
| --- | ---: | ---: | ---: |
| `no-fillings` | 909 / 32 812 байт | **−36 мс** | 8/8 быстрее |
| `no-content-block` | 935 / 32 807 байт | **−20 мс** | 7/8 быстрее |
| `comment` (всё ниже hero) | 479 / 32 822 байта | **−124 мс** | 8/8 быстрее |

Базис — 1112 узлов / 32 797 gzip-байт. Для `no-fillings` HTML responseEnd сдвигался примерно на −15 мс даже при почти равном gzip, поэтому **все 36 мс нельзя приписать только layout**. Дополнительный пилот по 4 пары: отзывы **−24 мс**, контакты **−28 мс**, оба 4/4; для релизного решения мало. Затраты распределены по нужному пользователю тексту, а не вызваны одним удаляемым декором.

Для отдельного сравнения со **всеми исполняемыми скриптами** обнаружено ограничение fixture: заголовок `Cache-Control: no-store` на *статических* CSS в сочетании с inline-скриптами вызывал в Chromium **повторный запрос каждого из шести CSS** (12 вместо 6). Этот результат отброшен как артефакт стенда, **не баг сайта**. В `full,live` и `live,main-enh-low` runner отдаёт cacheable-ассеты (`max-age=600`), но создаёт новый контекст для каждого холодного прогона; дублей CSS нет. При ×4 в 8 парах `live` против no-JS `full`: FCP=LCP **1094→1422 мс**, парная разница **+324 мс** (8/8), CSS responseEnd **+315 мс**. Локальные запросы пяти `defer`-скриптов начинаются ещё до завершения CSS и конкурируют за канал; в JS-варианте меняются также HTML и DOM. Это не raw CI trace и **не доказательство production-причины**.

Проверен потенциально меньший риск: тестово выставить `fetchpriority="low"` существующим `main.js`, `mc-2026.js` и `v20-faq-fix.js`, оставив `nav.js` и consent без изменения. В **8 парах** `live,main-enh-low` медиана парной разницы LCP всего **−6 мс**, знаки **4 быстрее / 4 медленнее**, CSS responseEnd **−0,85 мс**. Патч отвергнут: выигрыша нет, доступность корзины/интерактивности раньше первого кадра можно ухудшить.

## Продолжение: загрузка JS против его выполнения; ранний CSS (только fixture)

В runner добавлены четыре тестовых режима, **без правки сайта**. Новый контекст на каждую холодную загрузку, gzip/h2, CPU×4, 8 пар, те же viewport/шрифтовый mock; порядок вариантов циклически меняется:

```sh
node scripts/diagnostics/home_dom_lcp.cjs 8 live,live-no-exec,live-no-fetch 4
node scripts/diagnostics/home_dom_lcp.cjs 8 live,live-style-preload,live-css-preload 4
```

`live-no-exec`: **HTML и 5 адресов JS не меняются**, тестовый сервер оборачивает скачанный код в `if (false)`, сохраняя почти тот же gzip (≈65,8 против 65,7 КиБ для JS); выполнения нет. При медиане парной LCP **+16 мс** (3 быстрее / 5 медленнее) `ScriptDuration` падает примерно на **73 мс**, DOMContentLoaded на **163 мс**, окончание CSS на **1 мс**. То есть **в этом стенде** работа исполняемого JS не объясняет первый кадр. `live-no-fetch`: только во временном HTML пять внешних `<script>` имеют инертный `type`, запросов JS нет; HTML gzip **+28 байт**. Медиана парной LCP **−308 мс (8/8)**, CSS responseEnd **−305 мс (8/8)**, окончание загрузки hero AVIF **−184 мс (8/8)**. `live-no-exec` и `live-no-fetch` имеют одинаковые **1121 DOM-узел** и **побайтно одинаковые просмотренные PNG**; `live` с рабочей мобильной навигацией — 1669 узлов. Во всех 24 загрузках: 6 CSS-запросов, h2, `.hero-img` 640 px, CLS=0 и JS/local errors=0. Это **контроль конкуренции запросов на локальном h2-сервере**, а не разрешение отключить навигацию/корзину/consent в production и не production trace.

Менее инвазивный кандидат: добавить ранний `<link rel="preload" as="style">` для `style.css` либо для всех 6 CSS, оставив их порядок и содержимое неизменными. В **двух независимых сериях по 8 пар**: одиночный preload дал **−4 / −8 мс** (смешанные знаки); все шесть — **+10 / −22 мс** (смена знака между сериями). Во второй серии первый CSS стартовал на 28/15 мс раньше, но AVIF hero завершался на **+15/+22 мс позже**. CSS по-прежнему запрашивался ровно 6 раз, JS — 5, h2/CLS/errors как выше; PNG `live` и оба preload-варианта **побайтно совпали**. Стабильного выигрыша LCP нет, конкуренция может замедлять hero. **Не выпускать preload или задержку JS только по этому fixture**: реальные приоритеты CDN, шрифты и raw Lighthouse trace не проверены.

## QA, ограничения и решение

- На неизменном сайте в первом прогоне: `npm ci` и audit — **0 vulnerabilities**; `npm run qa` — **265 passed / 5 skipped**, статический аудит **49 passed / 0 warnings / 0 errors**. Реальный HTML+JS/CSS: 8 состояний (главная/бенто × mobile 390 / desktop 1440 × light/dark), PNG просмотрены; JS/local request errors **0**, axe WCAG A/AA violations **0** (**1–4 inconclusive**), CLS mobile **0**, desktop максимум **0,000438**; декодирование hero mobile **640 px**, desktop главной **1440**, бенто **1280 px**. Внешние шрифты помечены `skipped: sandbox egress`; `document.fonts.status=loaded` здесь означает работу с fallback, **не** проверку CDN. Chromium-эмуляция — не нативный Safari.
- Повтор после нового `npm ci` на том же SHA: первый `npm run qa` завершился с кодом 0, но **264 passed / 5 skipped / 1 flaky** (mobile `cart-accessibility.spec.js`, фокус `#cartClearNo`); изолированные 3 повтора без retry: **2 failed / 1 passed**. После dev-only правки этого runner повторный **полный QA вышел с кодом 1: 264 passed / 5 skipped / 1 failed**, тот же тест упал и на retry; статический аудит остался **49/0/0**, npm audit — 0 vulnerabilities, Pages build/audit PASS. QA не загружает runner, production-код не менялся; ошибка проявлялась до нынешнего diff. Возможная гонка фокуса корзины вне performance-scope; sandbox Chromium `153.0.8010.0` отличается от ожидаемого Playwright `153.0.8010.12`. **Не считать тот локальный QA зелёным** и не «чинить» корзину в performance PR без отдельного расследования; три проверки CI для `bf00c43` прошли.
- Перед новым опытом `npm ci` — 0 vulnerabilities, исходный `npm run qa` **265 passed / 5 skipped, exit 0**. После изменения **только** отчёта и dev-only runner повторный полный QA — **264 passed / 5 skipped / 1 failed, exit 1**: прежний mobile-тест `#cartClearNo` упал также на retry. Статические аудиты **49/0/0**, Pages build/audit на 33 страницах PASS при одинаковом `RELEASE_SHA` для обеих команд. QA не импортирует диагностический runner, production-код и тесты не менялись; прежнюю нестабильность не считать новым performance-регрессом или детерминированно зелёным тестом.
- В текущем проходе на HEAD `5ff9d1c` после `npm ci` — **0 vulnerabilities**; полный локальный `npm run qa` **до и после документирования** новых контролей завершился с кодом 0: **265 passed / 5 skipped** в каждом прогоне. Прежние красные прогоны выше сохраняются в журнале; новому SHA ещё нужна собственная CI-проверка. Исходные 3 проверки CI для `5ff9d1c` были PASS.
- `content-visibility` у текстовых секций **уже удаляли** в `css/mc-2026.css` и `css/premium-overrides.css` из-за риска SEO/поиска на странице/a11y. Удаление или перенос нижеэкранного DOM за JS разрушает содержимое/режим без JS. Не выдавать экспериментальные `hero`/`comment` за исправление.
