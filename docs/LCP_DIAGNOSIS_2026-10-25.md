## Продолжение: загрузка JS против его выполнения; ранний CSS (только fixture)

В runner добавлены четыре тестовых режима, **без правки сайта**. Новый контекст на каждую холодную загрузку, gzip/h2, CPU×4, 8 пар, те же viewport/шрифтовый mock; порядок вариантов циклически меняется:

```sh
node scripts/diagnostics/home_dom_lcp.cjs 8 live,live-no-exec,live-no-fetch 4
node scripts/diagnostics/home_dom_lcp.cjs 8 live,live-style-preload,live-css-preload 4
```

`live-no-exec`: **HTML и 5 адресов JS не меняются**, тестовый сервер оборачивает скачанный код в `if (false)`, сохраняя почти тот же gzip (≈65,8 против 65,7 КиБ для JS); выполнения нет. При медиане парной LCP **+16 мс** (3 быстрее / 5 медленнее) `ScriptDuration` падает примерно на **73 мс**, DOMContentLoaded на **163 мс**, окончание CSS на **1 мс**. То есть **в этом стенде** работа исполняемого JS не объясняет первый кадр. `live-no-fetch`: только во временном HTML пять внешних `<script>` имеют инертный `type`, запросов JS нет; HTML gzip **+28 байт**. Медиана парной LCP **−308 мс (8/8)**, CSS responseEnd **−305 мс (8/8)**, окончание загрузки hero AVIF **−184 мс (8/8)**. `live-no-exec` и `live-no-fetch` имеют одинаковые **1121 DOM-узел** и **побайтно одинаковые просмотренные PNG**; `live` с рабочей мобильной навигацией — 1669 узлов. Во всех 24 загрузках: 6 CSS-запросов, h2, `.hero-img` 640 px, CLS=0 и JS/local errors=0. Это **контроль конкуренции запросов на локальном h2-сервере**, а не разрешение отключить навигацию/корзину/consent в production и не production trace.

Менее инвазивный кандидат: добавить ранний `<link rel="preload" as="style">` для `style.css` либо для всех 6 CSS, оставив их порядок и содержимое неизменными. В **двух независимых сериях по 8 пар**: одиночный preload дал **−4 / −8 мс** (смешанные знаки); все шесть — **+10 / −22 мс** (смена знака между сериями). Во второй серии первый CSS стартовал на 28/15 мс раньше, но AVIF hero завершался на **+15/+22 мс позже**. CSS по-прежнему запрашивался ровно 6 раз, JS — 5, h2/CLS/errors как выше; PNG `live` и оба preload-варианта **побайтно совпали**. Стабильного выигрыша LCP нет, конкуренция может замедлять hero. **Не выпускать preload или задержку JS только по этому fixture**: для этих кандидатов не проверен парный production CDN/шрифтовый A/B; raw trace неизменённого сайта разобран отдельно выше.

## Подготовка проверки на реальных посещениях — только PR, без выпуска

После лабораторных опытов разница #102/#103 на production CDN по-прежнему не объяснена. Следующий этап — **не новая «оптимизация» без причины**, а возможность отличить реальный медленный хвост от нестабильной симуляции Lighthouse. Текущий PR подготовил opt-in событие `web_vital_lcp` для главной и бенто в **существующем** `js/consent-analytics.js`: PerformanceObserver запускается **только после согласия** на аналитику, но `buffered:true` позволяет прочитать уже случившийся LCP при согласии на первом визите. До согласия не создаётся LCP-наблюдатель и не отправляются аналитические запросы; отказ/отзыв не отправляют событие. Одно событие на навигацию передаёт GA4 числовой LCP, тип страницы, тип кандидата (`hero`/`other`), узкий/широкий viewport, тип навигации, признак ранее выданного согласия, доступные raw timing ответа HTML/изображения **без адресов и текста**. Ограничения: это **выборка лишь давших согласие**, она не эквивалентна CrUX/p75 всех посетителей; если браузер не поддерживает LCP PerformanceObserver, события нет. На мобильном первом визите LCP-кандидатом может быть текст под открытым consent, а не hero из Lighthouse: сегменты `lcp_consent` и `lcp_element` нельзя смешивать при анализе. Доставка события из GA на `pagehide` best-effort; **значений нового события в GA4 нет до отдельного одобренного deploy**; публичный CrUX для всего сайта здесь не установлен. Чтобы использовать числовой параметр `lcp_ms` в GA4, потребуются доступ к соответствующей собственности и регистрация custom metric; никаких логинов/ключей в репозитории нет. В этом PR **не меняются порог 2500 мс, число Lighthouse-прогонов и production performance-код hero/CSS**. Любой последующий патч допустим только после проверки полевой проблемы, парного контроля, визуального QA и измерения эффекта после разрешённого выпуска.

**Контроль точности opt-in-репортёра, следующий проход 26.10:** программный `pointerdown` раньше завершал измерение до реального ввода. Теперь завершение по `click`/`keydown` требует доверенного действия пользователя; `pagehide`/скрытие страницы остаются резервным завершением. Исторический `visibility-state` (если поддерживается браузером) исключает LCP-кандидаты после первого скрытия даже при позднем согласии. Пререндер исключён из этой выборки: иначе его время *до активации* искажало бы сравнение с cold Lighthouse; восстановления из BFCache и soft navigations тоже не включены. Убран дублирующий вычислимый параметр `lcp_after_resource_ms` (при наличии `lcp_resource_end_ms` интервал восстанавливается как `lcp_ms − lcp_resource_end_ms`). **Это не полная реализация всех сценариев CrUX/web-vitals**: браузер без истории visibility при позднем согласии может дать неполный контроль первого скрытия. Ни один из этих корректирующих шагов не ускоряет сайт.

Локальный fade-контроль и парные live-контроли Ken Burns и consent **не подтверждают эти механизмы как необходимые триггеры**; смешанные разницы и смена LCP-кандидата запрещают превращать их в speed patch. Исправляемый двойной WebP/AVIF preload Гатчины — отдельный доказанный избыточный запрос и эффект *raw* при ограниченной сети/CPU, **не** объяснение всех URL или снятие живого CI-warning. Вклад конкретного CSS/JS/шрифтов/CDN/планировщика и реальный field p75 остаются **неизвестными**.
