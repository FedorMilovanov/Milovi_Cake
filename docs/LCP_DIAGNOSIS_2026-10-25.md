В выбранных raw resources hero и `style.css` отвечали **200/h2, без SW**, Lighthouse runtime errors и console errors **0/12**; CLS — **0,02** только у бенто-`01`, **0** у остальных 11.

Визуально просмотрены исходные **224×498 JPEG screencast** из [CI-запуска 40253227018](https://github.com/FedorMilovanov/Milovi_Cake/actions/runs/40253227018): медленный бенто-`01` ранний кадр показывает hero до открытия consent, поздний — открытый dialog; **быстрый `03` на raw LCP тоже показывает открытый dialog**; медленный `04` на raw LCP — без видимого dialog. Следовательно, одно только наличие consent на кадре не различает быстрый и медленный исход. Флаг поиска `Paint` с nodeName overlay сам по себе **не равен состоянию UI** (он истинный у `04`, где dialog на выбранном кадре не виден). У главной `03` на raw LCP есть hero-фото, но ещё нет заголовка и нижней навигации, которые видны на таком же кадре быстрого `04`. Это кадры **raw**, а не кадры в *simulated* LCP-время; JPEG уменьшены Chromium и не заменяют полноразмерный скриншот/нативный Safari. Тёмная полоса снизу на бенто соответствует верхней тёмной части реального AVIF-изображения, не пустому плейсхолдеру.

**Решение:** не выпускать HTML/CSS/JS-«оптимизацию» по этим данным. Стабильная конкретная причина исторического предупреждения #102→#103 не установлена; для production-кандидата нужны парные одинаково настроенные прогоны старого/нового кода на одном окружении, контроль первого и конечного кадра, CLS, QA и выигрыш без регрессий. Временный CI-job и его анализатор удалены из PR отдельным cleanup-коммитом; сохранённый artifact и check annotations останутся доступны согласно правилам GitHub Actions.

## Новый контролируемый опыт: нижеэкранный DOM главной

Воспроизводимый dev-only скрипт: [`scripts/diagnostics/home_dom_lcp.cjs`](../scripts/diagnostics/home_dom_lcp.cjs). На машине с `npm ci`, Playwright Chromium и OpenSSL:

```sh
node scripts/diagnostics/home_dom_lcp.cjs 8 full,hero,comment
node scripts/diagnostics/home_dom_lcp.cjs 8 full,contain
```

Только тестовый сервер: локальные HTTPS + gzip + **h2**, один HTML/одни CSS, новый browser context и отключённый cache на каждом запуске. 390×844, `isMobile`, DPR 2, light, reduced-motion, RTT 100 мс, 1600 Кбит/с, CPU ×1/×4; порядок вариантов циклически менялся. Google Fonts недоступны в sandbox: один и тот же **пустой CSS font mock** для всех вариантов. Выполняемые скрипты сайта удалены **в обоих сравниваемых ответах** (исходники в репозитории не менялись), чтобы отделить HTML/стили от runtime. Footer и мобильная панель остаются одинаковыми.

- `full`: вся главная без исполняемых скриптов — **144 685 HTML-байт / 32 797 gzip**, 1112 DOM-элементов.
- `hero`: нижеэкранные секции в `<main>` убраны только в памяти тестового сервера, footer сохранён — **82 279 / 19 562 gzip**, 479 элементов.
- `comment`: те же нижеэкранные секции вместо DOM находятся в HTML-комментарии; **144 748 / 32 822 gzip**, 479 элементов. Эта пара почти уравнивает время/размер передачи HTML и CSS при одинаковом первом экране.
- `contain`: полный DOM и HTML, тестовый CSS дополняется `#main-content > section:not(.hero) { contain: layout style; }`. Ничего из этого в production CSS не добавлено.

**Медианы 8 пар в каждом режиме** (ms; `delta` = вариант − `full`):

Для отдельного сравнения со **всеми исполняемыми скриптами** обнаружено ограничение fixture: заголовок `Cache-Control: no-store` на *статических* CSS в сочетании с inline-скриптами вызывал в Chromium **повторный запрос каждого из шести CSS** (12 вместо 6). Этот результат отброшен как артефакт стенда, **не баг сайта**. В `full,live` и `live,main-enh-low` runner отдаёт cacheable-ассеты (`max-age=600`), но создаёт новый контекст для каждого холодного прогона; дублей CSS нет. Локальные запросы пяти `defer`-скриптов начинаются ещё до завершения CSS и конкурируют за канал; в JS-варианте меняются также HTML и DOM. Это не raw CI trace и **не доказательство production-причины**.

Патч отвергнут: выигрыша нет, доступность корзины/интерактивности раньше первого кадра можно ухудшить.

## Продолжение: загрузка JS против его выполнения; ранний CSS (только fixture)

В runner добавлены четыре тестовых режима, **без правки сайта**. Новый контекст на каждую холодную загрузку, gzip/h2, CPU×4, 8 пар, те же viewport/шрифтовый mock; порядок вариантов циклически меняется:

```sh
node scripts/diagnostics/home_dom_lcp.cjs 8 live,live-no-exec,live-no-fetch 4
node scripts/diagnostics/home_dom_lcp.cjs 8 live,live-style-preload,live-css-preload 4
```

`live-no-exec`: **HTML и 5 адресов JS не меняются**, тестовый сервер оборачивает скачанный код в `if (false)`, сохраняя почти тот же gzip (≈65,8 против 65,7 КиБ для JS); выполнения нет. При медиане парной LCP **+16 мс** (3 быстрее / 5 медленнее) `ScriptDuration` падает примерно на **73 мс**, DOMContentLoaded на **163 мс**, окончание CSS на **1 мс**. То есть **в этом стенде** работа исполняемого JS не объясняет первый кадр. `live-no-fetch`: только во временном HTML пять внешних `<script>` имеют инертный `type`, запросов JS нет; HTML gzip **+28 байт**. Медиана парной LCP **−308 мс (8/8)**, CSS responseEnd **−305 мс (8/8)**, окончание загрузки hero AVIF **−184 мс (8/8)**. `live-no-exec` и `live-no-fetch` имеют одинаковые **1121 DOM-узел** и **побайтно одинаковые просмотренные PNG**; `live` с рабочей мобильной навигацией — 1669 узлов. Во всех 24 загрузках: 6 CSS-запросов, h2, `.hero-img` 640 px, CLS=0 и JS/local errors=0. Это **контроль конкуренции запросов на локальном h2-сервере**, а не разрешение отключить навигацию/корзину/consent в production и не production trace.

Менее инвазивный кандидат: добавить ранний `<link rel="preload" as="style">` для `style.css` либо для всех 6 CSS, оставив их порядок и содержимое неизменными. В **двух независимых сериях по 8 пар**: одиночный preload дал **−4 / −8 мс** (смешанные знаки); все шесть — **+10 / −22 мс** (смена знака между сериями). Во второй серии первый CSS стартовал на 28/15 мс раньше, но AVIF hero завершался на **+15/+22 мс позже**. CSS по-прежнему запрашивался ровно 6 раз, JS — 5, h2/CLS/errors как выше; PNG `live` и оба preload-варианта **побайтно совпали**. Стабильного выигрыша LCP нет, конкуренция может замедлять hero. **Не выпускать preload или задержку JS только по этому fixture**: для этих кандидатов не проверен парный production CDN/шрифтовый A/B; raw trace неизменённого сайта разобран отдельно выше.

- Повтор после нового `npm ci` на том же SHA: первый `npm run qa` завершился с кодом 0, но **264 passed / 5 skipped / 1 flaky** (mobile `cart-accessibility.spec.js`, фокус `#cartClearNo`); изолированные 3 повтора без retry: **2 failed / 1 passed**. После dev-only правки этого runner повторный **полный QA вышел с кодом 1: 264 passed / 5 skipped / 1 failed**, тот же тест упал и на retry; статический аудит остался **49/0/0**, npm audit — 0 vulnerabilities, Pages build/audit PASS. QA не загружает runner, production-код не менялся; ошибка проявлялась до нынешнего diff. Возможная гонка фокуса корзины вне performance-scope; sandbox Chromium `153.0.8010.0` отличается от ожидаемого Playwright `153.0.8010.12`. **Не считать тот локальный QA зелёным** и не «чинить» корзину в performance PR без отдельного расследования; три проверки CI для `bf00c43` прошли.
- Перед новым опытом `npm ci` — 0 vulnerabilities, исходный `npm run qa` **265 passed / 5 skipped, exit 0**. После изменения **только** отчёта и dev-only runner повторный полный QA — **264 passed / 5 skipped / 1 failed, exit 1**: прежний mobile-тест `#cartClearNo` упал также на retry. Статические аудиты **49/0/0**, Pages build/audit на 33 страницах PASS при одинаковом `RELEASE_SHA` для обеих команд. - В текущем проходе на HEAD `5ff9d1c` после `npm ci` — **0 vulnerabilities**; полный локальный `npm run qa` **до и после документирования** новых контролей завершился с кодом 0: **265 passed / 5 skipped** в каждом прогоне. Прежние красные прогоны выше сохраняются в журнале; новому SHA ещё нужна собственная CI-проверка. Исходные 3 проверки CI для `5ff9d1c` были PASS.
- `content-visibility` у текстовых секций **уже удаляли** в `css/mc-2026.css` и `css/premium-overrides.css` из-за риска SEO/поиска на странице/a11y. Удаление или перенос нижеэкранного DOM за JS разрушает содержимое/режим без JS. Не выдавать экспериментальные `hero`/`comment` за исправление.

Она воспроизводит и быстрые, и медленные исходы, но без old/new-пары не устанавливает причину *разницы релизов* #102→#103. Нельзя обещать сокращение LCP от документационного PR; штатный CI Lighthouse запускается **после deploy**, не на PR.
- После временного CI-анализа на ветке с диагностикой (`51f1e13`, `65aee7c`, `295e941`, `313e376`) локальные полные QA были **265 passed / 5 skipped**, Pages artifact audit — **33 HTML OK**; CI на всех четырёх SHA завершился успешно (последний — [40253227018](https://github.com/FedorMilovanov/Milovi_Cake/actions/runs/40253227018): `qa`/review **success**, повторный capture **skipped**). Один одновременный локальный Pages build создал untracked `_site/` прямо посреди статического аудита QA и породил **37 ложных ошибок** сканирования сгенерированного каталога. Этот прогон **не считаем зелёным**: после удаления только собственного `_site/` полный QA повторён отдельно и прошёл **265 / 5**. Старые нестабильные результаты фокус-теста корзины выше не скрыты и не исправлялись в performance scope.
- **Решение самостоятельно:** оставить production HTML, CSS, runtime JS, SW и штатную конфигурацию CI без изменений; сохранить этот отчёт и dev-only runner в Git, временную диагностику убрать. Не мержить и не закрывать PR. Следующий инженерный шаг — при безопасном production-кандидате провести **парный same-run old/new A/B** под одинаковыми условиями с raw traces, ранним/конечным кадром, LCP/CLS и полным QA; если выигрыша без UX/SEO/a11y-регрессий нет, не выпускать патч.
