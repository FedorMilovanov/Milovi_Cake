# Аудит брошенного: репозиторий и Actions

Дата: 2026-10-29. Ветка `arena/d2a9652f-milovi-cake`.

Задача: найти всё, что осталось от прежних волн и больше не работает, но мешает
или вводит в заблуждение. Ветка `arena/91717241-milovi-cake` (PR #107) в аудит
не входит — ею занят другой агент.

## Метод

Проверялось по фактам, а не по названиям: для каждого подозрительного объекта
смотрел, существует ли файл в репозитории и в ветках, есть ли у него история
запусков, отличается ли содержимое ветки от `main`, и упоминается ли объект
где-нибудь ещё. Всё, что можно было измерить, измерено; выводы без измерения
помечены отдельно.

## 1. Actions: 73 «призрачных» workflow против 10 живых

| показатель | значение |
|---|---|
| записи в Actions | 85 (в том числе 2 динамических) |
| живых файлов в `.github/workflows/` | **10** |
| «призраков» (файла нет нигде) | **73** |
| самый старый запуск призрака | 2026-07-28 |
| самый свежий запуск призрака | 2026-10-28 |

Типичные имена призраков: `_temp-qa-diagnostic.yml`, `tmp-lighthouse-phase2.yml`,
`temporary-lcp-frame-trace.yml`, `gallery-phone-card-patch.yml`,
`dns-incident-bootstrap.yml`. Это одноразовые workflow из прошлых расследований:
сделали работу, файл удалили, запись осталась.

**Функционального риска нет.** Запустить призрак нельзя — файла нет.
GitHub API не предоставляет удаление записи workflow; она исчезает только
когда истекают сроки хранения всех её запусков (по умолчанию 90 дней).

**Важная оговорка.** `browser-compatibility.yml` в списке выглядит призраком, но
им не является: его файл лежит в ветке `arena/91717241-milovi-cake` (PR #107), и
последний запуск был 2026-10-29. Если бы я удалял «всё, чего нет в main», снёс бы
живой workflow чужой волны.

**Вывод:** косметика интерфейса Actions, чинится временем, а не действием.

## 6. Что сделано в этой волне

Восстановлен потерянный страж контраста `tests/contrast-regressions.spec.js`.

При переносе он не просто скопирован: два селектора устарели за семь недель,
и я разобрался с каждым отдельно, а не выбросил проверку.

| проблема | решение |
|---|---|
| `.site-footer .footer-brand …` не находил элемент | класс переименован в `.footer-col--brand`; сам селектор сохранён **вместе с `.w`** — цвет живёт на спанах, их создаёт JS, и проверять надо именно их |
| `.btn-primary.btn-warn` на Гатчине не находил элемент | блок и класс удалены из шаблона пригородов в сентябре; проверка убрана **с письменным объяснением в файле**, а не молча |

Проверки стража:

| проверка | результат |
|---|---|
| тест на текущем `main` | **2 passed** |
| контраст текста футера | 6,70:1 (порог AA — 4,5) |
| страж реагирует на регресс | подмена цвета на почти-фоновый даёт **1,09:1** → тест падает |
| `npm run audit` | PASSED (новый файл внесён в `DEV_TOOLING_JS`) |

Отдельно про честность измерения: первая моя проверка «страж не реагирует»
была ошибочной — в быстром скрипте я подставил не тот фон (кремовый вместо
фактического тёмного футера) и получил 2,58:1 там, где на самом деле 6,70:1.
Ошибка была в проверке, а не в тесте.
