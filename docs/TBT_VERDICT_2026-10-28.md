# Красный Lighthouse на `c0d1a51`: расследование TBT-провала, 28.10.2026

> **Вердикт коротко.** Провал рана — **одна** error-ассерция `total-blocking-time` (порог 300, медиана трёх прогонов = **529,709 мс**) на `/zakazat-tort-spb/`. Страница побайтово идентична зелёному рану 26 часов назад (`index.html` blob `51bf9565…`, sha256 `ad0df94a…`; `js/`, `css/`, `sw.js` — пустой diff). **Три независимые сессии 28.10 на тех же байтах дали 55 / 0 / 156,5 мс** (17 прогонов: медиана 40,5, 3 из 17 выше 300), то есть красное значение **не воспроизводится** — статус **proof**. **Причина числа установлена на уровне механизма:** гейт проверяет не измерение, а модель Lantern — в одной сессии на одних байтах симулированный TBT дал 0–797 мс, а наблюдаемый при реальном 4× CPU-троттлинге — 36–104 мс — тоже **proof**. Полевой p75 по-прежнему **неизвестен**. Пороги, production runtime и CI не менялись; временные workflow и конфиги удалены.

## 3. Декомпозиция TBT на `/zakazat-tort-spb/`

Ассерция использует **медиану трёх прогонов**. В красном ране три значения: **`[27; 575,229; 529,709]`** → медиана `529,709`. В зелёном: **`[56,5; 11,5; 40,5]`** → медиана `40,5`. То есть **один из трёх прогонов новой сессии был совершенно нормальным (27 мс)**: вердикт определило то, что «медленных» прогонов оказалось два, а не три и не один.

Репрезентативный отчёт красного рана ([`1793209237159-39334`](https://storage.googleapis.com/lighthouse-infrastructure.appspot.com/reports/1793209237159-39334.report.html)): perf **85**, FCP 1541, LCP 2060, **TBT 530**, CLS 0, TTI 2864. Разложение главного потока (наблюдаемый трейс, без симуляции):

| категория | красный | зелёный (3 прогона) |
| --- | ---: | ---: |
| Other | **1427 мс** | 392 / 544 / 772 |
| Style & Layout | 633 мс | 381 / 313 / 217 |
| Rendering | 45 мс | 25–37 |
| **Script Evaluation** | **37 мс** | 36–41 |
| Parse HTML & CSS | 29 мс | 21–25 |
| Script Parsing & Compilation | 7 мс | 6,6–6,7 |
| **итого main-thread** | **2178 мс** | 870 / 957 / 1086 |

Длинные задачи красного прогона №3: `Unattributable` 457 мс @1502,6; `/zakazat-tort-spb/` 409 мс @1093,6; `/js/consent-analytics.js` 357 мс @2885,2; документ 185 мс @869,6; `consent-analytics.js` 65 мс @3242,2; документ 50 мс @819,6. Сторонний код блокировал поток на **0 мс** (Google Fonts 112 KiB, 0 мс).

Выводы из чисел:
- **Сайтовый JS не является причиной.** Исполнение скриптов 37–55 мс за весь прогон (включая consent 8 KiB); парсинг/компиляция 7 мс; сторонние 0 мс. Блокировка живёт в «Other» и Style & Layout — это задачи, которые Lighthouse не приписывает скрипту.
- Прирост «Other» (220,6 → 1258,4 мс медиана) — это **ожидание внутри задач**, а не новый код: те же скрипты в зелёном ране дали 36–41 мс исполнения.
- Гейт меряет **симуляцию Lantern**, а не raw. `TotalBlockingTime.computeSimulatedMetric` → `LanternTotalBlockingTime`; `Simulator` умножает длительности CPU-задач на `cpuSlowdownMultiplier` (4 по конфигу), layout-задачи — на `4 × 0,5`; порог блокировки 50 мс; окно считается по симулированным FCP/TTI с коэффициентами 0,5/0,5. В красной сессии raw-длинные задачи дают в сумме ≈1,5 с (сверх порога 50 мс — ≈1,2 с), а гейт видит 0,53 с simulation: это разные величины, и simulated TBT зависит ещё и от сетевой части симуляции (окно FCP…TTI), а не только от CPU.

## 4. Семантика гейта (что именно проверяет CI)

`.github/lighthouse-config.json`: `numberOfRuns: 3`; `total-blocking-time` = **error**, `maxNumericValue: 300`, `aggregationMethod: median`; `largest-contentful-paint` = **warn**, 2500, median; `categories:performance` = warn, 0.85, median; a11y/best-practices/SEO/CLS = error, `pessimistic`.

Проверено по исходникам (без догадок):
- действие `treosh/lighthouse-ci-action@3e7e23fb` берёт `numberOfRuns` из конфига, если входной параметр `runs` не задан (`src/config.js`: `runs: getInput('runs') ? … : numberOfRuns || 1`), и передаёт его в `lhci collect` — три прогона реальны (артефакты содержат 24 LHR).
- `@lhci/utils@0.15.1 src/assertions.js`: `median` = для нечётного числа значений — центральное; **по умолчанию** `aggregationMethod = 'optimistic'`, а для `max*`-ассерций optimistic = `Math.min(values)`.
- Поэтому до коммита `f5e1569` («make Lighthouse aggregation explicit», 07.09) тот же TBT-гейт считался по **лучшему** из трёх прогонов. В истории это видно буквально: ран `71dde41f` прошёл с `[274,3; 661,2; 309,5]` (min 274,3), ран `b1d1e019` — с `[612,5; 353,4; 55,0]` (min 55). С явной медианой эти же данные были бы красными.
- Конфиг берётся из **аудируемого** SHA (workflow делает `checkout ref: AUDIT_SHA`), поэтому правка конфига не переигрывает прошлые релизы.
- Адекватность порога: 300 мс TBT — это не порог Core Web Vitals (там INP ≤ 200 мс), а более жёсткий лабораторный ориентир, помноженный на 4× CPU-симуляцию. Для страницы, у которой реальная работа потока — верстка каталога, этот гейт измеряет устойчивость раннера не меньше, чем сайт.

## 6. Что изменилось в окружении

1. **Сборка браузера.** Зелёный ран 27.10 — Chrome 155.0.0.0, все раны 17–27.10 — 155. Красный ран 28.10 — **Chrome 156.0.0.0**. Это единственное известное различие в **версии** измерительного инструмента между двумя идентичными байтами.
2. **Состояние раннера внутри сессии.** В красном ране главная, прогон №1: `benchmarkIndex = 342,5` (обычно 2450–2510), main-thread **10 399,9 мс**, TBT **2707,5**, LCP 3664, и **собственное предупреждение Lighthouse**: «The tested device appears to have a slower CPU than Lighthouse expects…». В зелёном ране аналогичный, но мягкий случай: главная, прогон №1, `benchmarkIndex = 1603` при TBT 299,5.
3. Шкала эффекта на неизменных байтах: main-thread у `/zakazat-tort-spb/` **870/957/1086 мс** (27.10) против **1709,8/2278,1/2178,5 мс** (28.10) — все три прогона нового рана выше максимума предыдущих 21. Одновременно `Script Evaluation` не изменился (36–41 vs 37–55 мс), а «Other» вырос в 5,7 раза.

Честная граница: `benchmarkIndex` измеряется в начале прогона и не поймал просадку в блоке `zakazat` (там он 2478–2493), а ранов на Chrome 156 ровно **один**. Поэтому **нельзя** утверждать «виноват Chrome 156» — только «изменилось окружение, а не байты», и что именно из двух факторов доминирует — открытый вопрос.

Косвенное подтверждение, что дело не в конкретном коде страницы: в том же красном ране `/`, `/gallery/`, `/o-konditere/`, `/privacy/`, `/prigorody/gatchina/` держали обычный TBT (63; 8; 0; 0; 33,5), а выросли только `/bento-torty/` (285) и `/zakazat-tort-spb/` (529,7) — два соседних по порядку сбора блока. Это совместимо с коротким окном деградации раннера, но не доказывает его.

## 11. Наблюдаемый vs симулированный TBT — решающий эксперимент

В одном раннере, в одной сессии, на одних и тех же байтах: конфиг C (`throttlingMethod: devtools`, реальный 4× CPU + реальная сеть 150 мс/1638 Кбит/с) и конфиг D (`simulate`, Lantern).

| страница | наблюдаемый TBT (C, devtools) | симулированный TBT (D, гейт) | отношение |
| --- | --- | --- | --- |
| `/zakazat-tort-spb/` | 73; 36,2; 44,6 (медиана **44,6**) | 156,5; 0; 283,2 (медиана **156,5**) | 0–7,8× |
| `/bento-torty/` | 104,1; 89,7; 67,5 (медиана **89,7**) | 235; 797,3; 611,2 (медиана **611,2**) | 2,3–7,7× |

Разброс внутри одной сессии: наблюдаемый TBT — в 1,5 раза (67,5–104,1), симулированный — в 3,4 раза (235–797,3). Причина не в «шуме ранера»: режимы различаются только способом расчёта метрики. Проверено по исходникам Lighthouse 12.6.1: `core/computed/metrics/metric.js` отправляет `throttlingMethod: 'simulate'` в `computeSimulatedMetric` (Lantern), а `'devtools'` и `'provided'` — в `computeObservedMetric` (расчёт по реальному трейсу). Lantern умножает длительности CPU-задач на `cpuSlowdownMultiplier` (4) и layout-задачи на `4 × 0,5` (`@paulirish/trace_engine models/trace/lantern/simulation/Simulator.js`), а окно TBT берёт из **симулированных** FCP/TTI. Отсюда и 3–8-кратное раздутие, и чувствительность к фазе симуляции.

Практический смысл: **реальная блокировка главного потока этих страниц — 36–104 мс**, то есть далеко от 300 мс и от порогов INP. Красный ран не описывает пользовательский опыт; он описывает поведение модели Lantern на конкретном прогоне. Чинить в сайте нечего: длинные задачи приписаны документу (вёрстка каталога), а не скриптам (`JavaScript execution time 0,0 s`, Script Evaluation 23–55 мс).

## 12. Предложение владельцу по робастному мониторингу (без правок CI сейчас)

Ничего из этого не внесено — только предложение, решение за владельцем.

1. **Перестать гейтить симулированный TBT при пороге 300.** Числа §11: на идентичных байтах симулированный TBT даёт 0–797 мс, наблюдаемый — 36–104 мс. Порог 300 лежит ровно в зоне разброса модели. Варианты по убыванию предпочтительности:
   - **мерить наблюдаемый TBT** отдельным шагом с `throttlingMethod: devtools` и тем же порогом 300 (запас 3–8×; измерение воспроизводимо: 67,5–104,1 мс на бенто, 36,2–73 на заказе);

- **Причина LCP-медианы 3921** не установлена: видны только 1 прогон из 3.

### 19.3 Почему 0: TBT считается по перестроенной шкале, а не по наблюдаемым задачам

В одном и том же локальном прогоне `simulate-bento-1`:

- аудит `long-tasks` (наблюдаемый трейс) видит **три задачи: 84 мс @900, 63 мс @837, 52 мс @2273**;
- `total-blocking-time` = **0**, список задач внутри аудита пуст;
- симулированные FCP/TTI в этом прогоне — **2415 / 3308**, то есть окно TBT шириной 893 мс лежит далеко позже наблюдаемых задач (последняя кончается на 2325 мс);
- при `devtools` те же задачи считаются как есть: FCP 746, TBT 42.

Вывод, который теперь доказан на уровне одного прогона: **TBT под `simulate` — это функция от того, куда Lantern поставил окно [FCP, TTI], а не от того, сколько страница нагружает поток.** Сдвиг окна на секунду меняет вердикт с «0 мс» на «красный» при неизменном трейсе. В CI окно накрывает длинные задачи: в красном ране 570,633 отчётной медианы соответствуют задачам 297 и 422 мс, начавшимся уже после FCP 1647 (их вклад по определению TBT — 247 + 372 = 619 мс; точное число даёт пересчёт Лантерна), локально окно проходит мимо них.

Обратная сторона: локальный сервер без gzip и keep-alive раздувает симулированную сеть, поэтому абсолютные FCP здесь (2,4 с у бенто) не сравнимы с продакшеном. **Сравнивать между средами можно только сам факт нестабильности, не миллисекунды.**

### 19.4 Где среда и CI согласны — главная страница

Единственная страница, где локальные и CI-числа сходятся:

| источник | TBT | LCP | что внутри |
| --- | ---: | ---: | --- |
| локально, `simulate` (медиана) | **79,5** | 5494–5770 | длинные задачи на `/js/main.js`: 117–215 мс |
| локально, `devtools` (медиана) | **103,3** | 5460–5498 | те же задачи на `/js/main.js`: 50–151 мс + одна 313–355 мс на документе |
| CI, медианы двух публичных отчётов | 12 и 100 | 3921; 4276 | Render Delay 84 % от LCP |

То есть у главной **есть реальная работа в `main.js` — 117–215 мс на задачу под `simulate` и 50–151 мс под `devtools`**, и она воспроизводится на другой машине, в другом режиме троттлинга и в CI. Это ниже порога 300, гейт её не ловит; зато гейт краснеет на бенто, где настоящей работы 50–90 мс.

LCP главной тоже устойчив: LCP-элемент — `img.hero-img` (`head_mobile-640.avif` на мобильном, атрибут `fetchpriority="high"` есть в разметке), но в фазах доминирует **Render Delay**: 3590 мс (CI), 4577 мс (`simulate` локально), 3903 мс (`devtools` локально) при Load Time 0–959 мс. Картинка готова задолго до того, как её показывают.

### 19.5 Что это меняет

1. **Приоритет backlog смещается с бенто на главную.** Бенто — монетка (0 локально, 285–611 в CI), главная — воспроизводимо: TBT ~80–105 мс собственной работой `main.js` и LCP 3,9–4,3 с в CI при Render Delay 84 %.
2. **«Мерить наблюдаемый TBT» из §12 — по-прежнему лучший вариант, но калибровать его надо по главной, а не по бенто.** Наблюдаемые значения: бенто 6,6–42 локально и 89,7 в CI; заказ 0 локально и 44,6 в CI; главная 83,7–137,4 локально. Порог 300 при наблюдаемом режиме не красит ничего и сохраняет запас 2–3× на главной.
3. **Гейт по TBT в текущем виде краснеет на странице, где работы меньше всего.** Это утверждение теперь подкреплено не только CI-репликациями (§10–§11), но и независимой машиной.
4. **Красный `main` второй раз подряд** — не сигнал о деградации: оба рана зелёные по a11y/BP/SEO и падают только на симулированном TBT.

### 19.6 Чего этот эксперимент не доказывает

- **Локальный сервер — не CDN.** `python3 -m http.server` не сжимает и не держит соединения, поэтому симулированная сеть и все FCP/LCP локально не сопоставимы с продакшеном; сопоставим только факт разброса TBT.
- **Chrome разный.** Локально 153.0.8010.0, в CI — сборка раннера (156 в сессиях 27–28.10). Вклад версии браузера не изолирован.
- **Одна машина, три прогона на точку.** Парного контроля «локально vs CI на одном SHA» нет по определению: среда разная.
- **Причина Render Delay 84 % на главной не установлена.** Кандидаты (порядок CSS, шрифты, `main.js`, согласие-оверлей) не проверялись по отдельности — это следующая волна.
- **22 из 24 LHR каждого CI-рана по-прежнему недоступны** (артефакт на `blob.core.windows.net` вне эгресса песочницы); известны медианы и два публичных отчёта.

### 19.7 Как это повторить (без CI и без правок репозитория)

```bash
# 1. Lighthouse той же версии, что в CI, — в отдельный каталог вне репозитория
npm i --prefix /tmp/lh lighthouse@12.6.1
# 2. Chromium (npm-сборка Sparticuz), библиотеки рядом
npm pack @sparticuz/chromium@153.0.0   # bin/chromium.br + bin/al2023.tar.br → brotli → /tmp/chromium
# 3. Любой статический сервер с корня репозитория
python3 -m http.server 4173
# 4. Прогон через API (settings — дословно из .github/lighthouse-config.json)
node -e "… lighthouse(url, {port}, {extends:'lighthouse:default', settings}) …"
```

Ключевая часть — `settings`: `onlyCategories: ['performance','accessibility','best-practices','seo']`, `formFactor: 'mobile'`, `screenEmulation {mobile:true,width:412,height:915,deviceScaleFactor:1.75}`, `throttling {rttMs:150,throughputKbps:1638.4,cpuSlowdownMultiplier:4}`, `throttlingMethod: 'simulate'` (или `'devtools'`). Результат складывается в `/tmp/lh-results/*.json` — это полные LHR, из них берутся `total-blocking-time`, `long-tasks`, `mainthread-work-breakdown`, `largest-contentful-paint-element` и `environment.benchmarkIndex`.

Ничего из этого не требует GitHub, не меняет `.github/lighthouse-config.json` и не пушит в `main`.

## 20. Главная страница: «Render Delay 84 %» не раскладывается на отдельный ресурс

§19 оставил главную единственным сигналом, который повторяется в двух средах, и предположил, что причина — работа в `js/main.js`. Этот раздел проверяет предположение ablation-экспериментом и **опровергает его для реалистичного транспорта**. Заодно исправляет пер-скриптовое разложение из §19.4 (см. §20.9).

### 20.1 Метод

Две одинаковые раздачи одного дерева:

| сервер | транспорт | зачем |
| --- | --- | --- |
| `python3 -m http.server` (:4173) | без сжатия, HTTP/1.0, без keep-alive | как в §19 — контроль «плохой транспорт» |
| node, gzip level 9 + keep-alive (:4174) | main.js 40 151 B вместо 154 434 B, style.css 39 324 B вместо 212 950 B | размеры передачи как в проде (LH по проду видит 38–40 KiB) |

Замеры — Playwright на Chromium 153, `Emulation.setCPUThrottlingRate 4`, сеть 150 мс / 1638,4 кбит/с (те же цифры, что в `.github/lighthouse-config.json`), FCP и LCP через `PerformanceObserver` (`paint` + `largest-contentful-paint`, buffered), по 2–3 загрузки на конфигурацию. Отдельно — Lighthouse 12.6.1 с конфигом гейта против gzip-сервера.

### 20.2 На главной LCP — это FCP

Во **всех 37 локальных загрузках** (обе раздачи, все варианты; проверено скриптом по сохранённым данным, расхождений 0) LCP-кандидат один и тот же и приходит в тот же момент, что и первая отрисовка:

| | значение |
| --- | --- |
| элемент | `img.hero-img`, `head_mobile-640.avif`, размер записи 107 120 |
| записей LCP за загрузку | **1** |
| `renderTime` LCP / FCP | совпадают во всех прогонах (`4480/4480`, `3392/3392`, `4364/4364`, `1456/1456`, `1492/1492`, …) |

То есть на главной «LCP 4,3 с» означает не «картинка долго грузилась», а «страница вообще впервые отрисовалась в 4,3 с». Любая работа, отодвигающая первую отрисовку, целиком уходит в LCP.

### 20.3 Ablation на gzip-сервере: ничего не выходит из шума

По одному заблокированному ресурсу за прогон, FCP в мс:

| конфигурация | прогон 1 | прогон 2 | медиана | Δ к baseline |
| --- | ---: | ---: | ---: | ---: |
| baseline | 1456 | 1440 | **1448** | — |
| без `main.js` | 1552 | 1500 | 1526 | +78 |
| без `nav.js` | 1812 | 1600 | 1706 | +258 |
| без `mc-2026.js` | 1600 | 1532 | 1566 | +118 |
| без `consent-analytics.js` | 1484 | 1540 | 1512 | +64 |
| без **всех** JS | 1300 | 1356 | **1328** | −120 |
| только `style.css` (5 оверрайдов заблокированы) | 1560 | 1312 | **1436** | −12 |

Разброс между двумя прогонами одной и той же конфигурации — до 250 мс; медианы отличаются от baseline на ±260 мс, причём **удаление `main.js` и `nav.js` делает первую отрисовку медленнее**, а не быстрее. Это шум, а не эффект. Вывод: на реалистичном транспорте ни один отдельный скрипт и ни один CSS-файл не отвечает за задержку первой отрисовки главной.

### 20.4 Контроль метода: без сжатия те же абляции «дают» секунду

Тот же скрипт против несжатого сервера (:4173, как в §19):

| конфигурация | медиана FCP | Δ к baseline |
| --- | ---: | ---: |
| baseline | 4464 | — |
| без `main.js` | 3906 | **−558** |
| без `nav.js` | 4286 | −178 |
| без `mc-2026.js` | 4256 | −208 |
| без `v20-faq-fix.js` | 4322 | −142 |
| без `consent-analytics.js` | 4252 | −212 |
| без **всех** JS | 3434 | **−1030** |

Отдельно, тем же Lighthouse 12.6.1 и тем же конфигом на том же несжатом сервере (§19.2): baseline FCP 3919; 3920; 3970 против «только `style.css`» 3020; 3010; 3032, то есть −900 мс за счёт одних оверрайдов. На gzip-сервере тот же приём даёт 1436 против 1448 (§20.3) — ноль.

Один и тот же код, одна машина, одни настройки — и «эффект» отличается в 4–8 раз только из-за того, что сервер не сжимает файлы. `main.js` весит 154 434 B сырых против 39 885 B в gzip: при 1,6 Мбит/с это 754 мс против 195 мс передачи. Именно эта разница и «нашлась» в §19.

Практическое правило для этого репозитория: **любой ablation-эксперимент по отрисовке обязан идти на сжатом и keep-alive транспорте, иначе он измеряет размер файла, а не стоимость выполнения.**

### 20.5 Lighthouse по gzip-серверу: главная почти здорова

Тот же конфиг гейта (simulate, mobile 412×915, CPU ×4, 3 прогона):

| страница | FCP | LCP | TBT | performance |
| --- | --- | --- | --- | --- |
| `/` | 1658; 1808; 1805 | 1885; 2474; 2448 | 283; 101; 81 | 0,93; 0,96; 0,96 |
| `/bento-torty/` | 1382; 1390; 1381 | 1668; 1680; 1666 | 0; 17; 0 | 0,99; 0,99; 0,99 |

Для сравнения, тот же Lighthouse и тот же конфиг против **несжатого** сервера (§19.2): главная FCP ~3912, LCP ~5708, performance 0,68; бенто LCP ~3,1 с.

То есть при нормальном транспорте главная на этой машине — это performance ≈0,95 и LCP ≈2 с, а не 0,75 и 4,3 с. Разница между локальной репликацией и CI (FCP 3,5 с, LCP 4,3 с) **не объясняется ни одним ресурсом страницы** и целиком относится к среде: реальный TTFB 690 мс против 454 мс в модели, число round-trip'ов до CDN по HTTP/2+TLS, класс раннера.

### 20.6 Шрифты исключены прямым тестом

Проверено не чтением, а задержкой: искусственный ответ на `fonts.googleapis.com` через **600 мс** не сдвинул ни FCP, ни LCP — 1484/1484, 1484/1484, 1496/1496 против контроля 1492/1492, 1464/1464, 1628/1628.

### 20.7 Чего гейт не видит на главной

TBT по определению суммирует задачи **после FCP**. Работа, которая на главной отодвигает первую отрисовку (main-thread breakdown Lighthouse на несжатом сервере: Other ~1108 мс, Style & Layout ~890 мс, Script Evaluation ~203 мс — то есть почти вся до FCP), в TBT не попадает вообще. Отсюда асимметрия, которую видно в двух последних ранах `main`:

| | главная | бенто |
| --- | --- | --- |
| performance в CI | 0,75–0,78 | 0,84–0,85 |
| LCP-медиана в CI | 3921 / 4276 | 1650–2561 |
| собственная работа JS | TBT 12 / 100 | 50–90 мс |
| вердикт гейта | зелёный (LCP — `warn`) | **красный** |

Гейт краснеет там, где работы меньше, и молчит там, где дороже всего. Это свойство метрики, а не страниц, и оно окончательно объясняет оба красных рана.

### 20.8 Что не проверено

- **Не разложен разрыв 1,5 с (локально, gzip) против 3,5 с (CI).** Удалённый прод-URL из песочницы недоступен (эгресс), трасс в артефактах нет — есть только LHR. Кандидаты (TTFB 690 мс, round-trip'ы до CDN, класс раннера) не разделены.
- **Chrome разный:** локально 153.0.8010.0, в CI — сборка раннера (156 в сессиях 27–28.10).
- **По 2–3 прогона на конфигурацию**, одна машина (2 vCPU). Двух прогонов хватает, чтобы увидеть шум, но не чтобы дать доверительный интервал.
- **HTTP/2 и TLS не воспроизведены:** локально HTTP/1.1 keep-alive, без TLS. Число round-trip'ов в проде больше, и это одна из причин разрыва из §20.5.
- **Не измерялся эффект объединения шести CSS в один файл** — это потребовало бы правки каскада, запрещённой `AGENTS.md` §4.1 без отдельного согласия.

### 20.9 Исправление к §19

Фраза §19.4 «работа сидит в `js/main.js` (117–215 мс на задачу)» верна как факт о трейсе, но **не подтверждается как причина задержки отрисовки**: на gzip-транспорте удаление `main.js` не ускоряет первую отрисовку (§20.3). В силе остаётся другое: главная — единственная страница, где локальные и CI-числа TBT согласуются (79,5/103,3 локально против 12 и ~100 в CI), и она же единственная, где реальная работа JS видна в трейсе.

### 20.10 Итог по волне

1. **Правок в вёрстку и скрипты не требуется и не предлагается.** Ни один отдельный ресурс не отвечает за задержку; доказательство — §20.3 против контроля §20.4.
2. **Сигнал «главная плохая» в CI следует читать как средовой**: TTFB и число round-trip'ов, а не работа страницы.
3. **Единственное, что стоит держать под наблюдением, — тренд, а не одиночный ран:** LCP-медиана главной 3921 → 4276 при неизменных байтах (§19.1).
4. **Ограничение бюджета CSS/JS уже работает** (`scripts/audit.py`: gzip CSS 84 266 B при бюджете 100 000, JS 79 983 B при 80 000, сумма 164 249 B при 180 000). Сайт сидит вплотную к потолку по JS — это единственная измеренная «дешёвая» зона, но ablation её выигрыша не показывает.

## 21. Красная страница меняется от окружения к окружению — эксперимент с множителем CPU

§19–§20 показали, что вердикт зависит от того, куда Lantern поставил окно `[FCP, TTI]`, а не от веса страницы. Оставался вопрос, который решает судьбу гейта: **какая страница «виновата» — свойство страницы или свойство машины?** Этот раздел отвечает прямым экспериментом: одни и те же байты, один сервер, один браузер, одна машина — меняется только `throttling.cpuSlowdownMultiplier`.

### 21.1 Метод

| параметр | значение |
| --- | --- |
| сервер | gzip + keep-alive на :4174 (тот же, что в §20; `main.js` 40 151 B, `style.css` 39 324 B) |
| Lighthouse | 12.6.1, конфиг гейта (`.github/lighthouse-config.json`) |
| браузер | Chromium 153.0.8010.0 |
| машина | 2 vCPU, load average < 0.3 перед стартом |
| страницы | `/bento-torty/`, `/` , `/privacy/` (контроль) |
| множитель CPU | **×4** (значение гейта), **×8**, **×12** |
| режимы | `simulate` (гейт) и `devtools` (наблюдаемый, реальное троттлинг-торможение) |
| прогонов | 2 на точку, всего 36 |

### 21.2 `simulate` — режим гейта: красной становится главная, а не бенто

TBT, мс (два прогона / медиана):

| страница | ×4 (гейт) | ×8 | ×12 |
| --- | --- | --- | --- |
| `/bento-torty/` | 0; 0 → **0** | 0; 0 → **0** | 54,5; 0 → **54,5** |
| `/` | 89,5; 96,5 → **96,5** | 195; 341,5 → **341,5** | **1076,5; 791,5 → RED** |
| `/privacy/` (контроль) | 0; 0 → 0 | 0; 0 → 0 | 0; 0 → 0 |

При пороге 300 мс и медиане из трёх:

- **×4** (ровно конфиг CI): красных нет вообще — ни бенто, ни главная;
- **×8**: главная пересекает порог (одна точка 341,5, вторая 195 — при трёх прогонах это была бы лотерея);
- **×12**: главная **глубоко красная** (791,5–1076,5 мс, то есть в 2,6–3,6 раза выше порога), а бенто остаётся зелёным.

Это зеркальное отражение CI: там краснеет бенто (5 сессий из 7) и никогда — главная. Здесь, на идентичных байтах, всё наоборот. Значит «страница, которая краснеет» — свойство пары «машина × множитель», а не свойство страницы.

### 21.3 `devtools` — режим наблюдаемых метрик: бенто краснеет, главная не измеряется вообще

TBT, мс, при реальном троттлинге:

| страница | ×4 | ×8 | ×12 |
| --- | --- | --- | --- |
| `/bento-torty/` | 59,8; 43,4 → **59,8** | 169,2; 185 → **185** | **470,9; 356,5 → RED** |
| `/` | 246; 218,7 → **246** | **метрика отсутствует** | **метрика отсутствует** |
| `/privacy/` | 0; 0 | 0; 0 | 0; 0 |

Три вывода, которых не было раньше:

1. **«Мерить наблюдаемый TBT» — не панацея.** При ×12 бенто даёт 356–471 мс наблюдаемого TBT, то есть тоже красный. Наблюдаемый режим устойчивее (при ×4 он даёт 43–60 вместо 0 у симуляции и держится на 1/5 порога), но не свободен от класса машины.
2. **Главная не поддаётся измерению наблюдаемым TBT на медленной машине.** Все четыре прогона при ×8/×12 вернули ошибку метрики (в таблице «метрика отсутствует»):
   `Your page took too long to load … (NO_TTI_CPU_IDLE_PERIOD)` — за 17–21 секунду трейса метрика не вычислена. В LHR `performance` = `null`. То есть переключение гейта на `devtools` превратило бы красный ран главной в отсутствие метрики (в LHCI это тоже не «pass»).
3. **«Главная не простаивает» — гипотеза, которая НЕ подтвердилась.** Напрашивалось объяснение: в наблюдаемом прогоне при ×4 длинные задачи идут до 13–16 с (10 482+66, 11 124+66, 11 577+64, 12 471+56, 13 446+50 мс), значит поток занят постоянно и окно простоя не наступает. Проверка это не подтвердила:
   - прогоны при ×8 **со** включёнными скриншотами и при ×8/×12 **с** `settings.disableFullPageScreenshot: true` дают **0 длинных задач во всём трейсе** — то есть поздние задачи из прогона ×4 не воспроизводятся вообще, и отключение скриншотов на них не влияет;
   - обычные прогоны Playwright (те же флаги, тот же dsf 1.75, та же сеть 150 мс/1638 кбит/с, CPU ×4 и ×8, наблюдение 20–22 с) после 5-й секунды не видят **ни одной** длинной задачи.

   Значит приписывать эти задачи сайту нельзя — но и объяснить их скриншотами Lighthouse нельзя: эксперимент их не изолирует. Задачи на 10,5–16 с в единственном прогоне остаются **неатрибутированными**.
   
   При этом `NO_TTI_CPU_IDLE_PERIOD` при ×8/×12 держится и без скриншотов, и при нуле длинных задач. Единственная поздняя активность в таком прогоне — пачка из 11 лениво загружаемых картинок (`cake_biscuit_0…5`, `bento_1`, `meringue_roll`, `pavlova`, `cupcakes`, `cake_3d`), запрошенных на 11 280–11 441 мс, то есть через ~7 с после `load` (4 084 мс). Почему Lighthouse не смог поставить TTI — **не установлено**.

### 21.4 Контроль: страница без работы не двигается ни на одном множителе

`/privacy/` дала TBT **0 во всех двенадцати прогонах этой матрицы** (плюс 0 во всех шести прогонах §19.2 и во всех 68 исторических CI-ранах). Значит машина не «сломана целиком»: двигаются только страницы с вёрсткой, и двигаются они **по-разному в зависимости от множителя**.

### 21.5 Механизм виден в одном прогоне

`simulate`, `/bento-torty/`, ×12, второй прогон: окно `[FCP 1381, TTI 1695]` шириной 314 мс, а длинные задачи — 601+325, 711+174, 885+166, 1051+110 мс, то есть **все заканчиваются до FCP**. Итог: **TBT = 0** при задаче длиной 325 мс. Первый прогон той же точки: те же задачи чуть длиннее, медиана TBT 54,5.

`simulate`, `/`, ×12: окно расширяется до `[1651, 3594]` — 1943 мс вместо 810 мс при ×4 — и внутрь попадает уже семь задач (287, 153, 143, 140, 133, 67, 59 мс), суммы которых хватает, чтобы дать 791–1076 мс. Разница между «0» и «1076» здесь — не работа сайта, а ширина окна и место задач относительно его границ.

### 21.6 Корректировка к §11

В §11 было записано, что `simulate` раздувает TBT в 3–8 раз относительно наблюдаемого. Эксперимент §20–§21 показывает, что **направление зависит от транспорта**: на несжатом сервере наблюдаемый TBT был ниже (36–104 против 156–611), а на gzip-сервере при ×4 главная даёт **наблюдаемый 218–246 мс против симулированных 89,5–96,5** — то есть наблюдаемый теперь выше в 2,3–2,7 раза. Причина та же: более быстрый транспорт опускает FCP, и в окно TBT попадает больше задач. Формулировка «simulate завышает» неверна как общая; верна только «simulate считает по перестроенной шкале».

### 21.7 Что из этого следует для решения по гейту

Сводка по всем известным окружениям на **одних и тех же байтах**:

| окружение | кто краснеет | числа |
| --- | --- | --- |
| CI, 7 сессий 27–28.10 | `/bento-torty/` | 252 · 285 · 487,5 · 611,2 · 570,633 · 320,959 · 664,5 → **5 из 7** |
| локально, `simulate` ×4 | никто | бенто 0, главная 96,5 |
| локально, `simulate` ×12 | **`/`** | главная 791,5–1076,5, бенто 54,5 |
| локально, `devtools` ×12 | **`/bento-torty/`** | бенто 356,5–470,9, главная не измеряется |

Ни одно правило агрегации не спасает: при ×12 медиана главной 1076,5, оптимистичный минимум — 791,5, оба глубоко выше 300. Единственные варианты, которые действительно гасят ложные красные, — снять с TBT уровень `error`, либо убрать симулированный TBT из гейта и мерить наблюдаемый на **фиксированном, явно записанном** классе машины с порогом, откалиброванным по её же разбросу.

Отдельно: при переходе на `devtools` гейт получит новую болезнь — **отсутствие метрики** там, где Lighthouse не может поставить TTI (главная при ×8/×12; причина не установлена, см. §21.3). Это нужно решать явно (считать ошибку метрики провалом или пропуском), иначе гейт будет краснеть на пустом месте.

### 21.8 Что не проверено

- **Одна машина** (2 vCPU), локально; `benchmarkIndex` 2052–2562 против 2450–4260 в CI. Класс сопоставим, но это не раннер.
- **Множитель ×12 — не реальный класс устройства.** Цель была не измерить телефон, а показать, что вердикт управляется множителем; «×8 похоже на раннер CI» — гипотеза, а не измерение: эффективный множитель CI-раннера неизвестен, потому что `benchmarkIndex` в аннотациях не публикуется.
- **По 2 прогона на точку.** Этого достаточно, чтобы увидеть разворот (0 против 1076), но недостаточно для интервала.
- **Chrome 153 локально** против сборки раннера (156 в CI-сессиях 27–28.10).
- **Причина `NO_TTI_CPU_IDLE_PERIOD` на главной при ×8/×12 не установлена** (§21.3, пункт 3). Исключены: длинные задачи (их ноль) и скриншоты Lighthouse (отключение не помогает). Не проверены: триггер поздней загрузки 11 картинок на ~11,3 с, поведение Service Worker и сетевые условия внутри LH.
- **Не измерялось, воспроизводится ли поздняя загрузка картинок без Lighthouse** — обычный прогон Playwright при прокрутке страницы не делался, поэтому «картинки грузятся поздно» пока утверждение только про прогон внутри Lighthouse.
- **HTTP/2 и TLS не воспроизведены** локально.

## 22. Пост-мерж прогон `306ec5b` — первое двойное падение, и решение по гейту

### 22.1 Факт

Прогон Lighthouse **`40802536703`** на `306ec5b` (то есть на `main` после мержа #111) — **красный**. Это первый ран за серию, где TBT упал на **двух** страницах одновременно, и первый, где упал `/svadebnye-torty/`.

| страница | ассерт | найдено | метрики того же рана |
| --- | --- | ---: | --- |
| `/bento-torty/` | TBT `error` (median) | **737** | Perf 0,81 · FCP 1114 · **LCP 1292** · TTI 2143 · CLS 0 · SI 1282; a11y/BP/SEO 100 |
| `/svadebnye-torty/` | TBT `error` (median) | **687,376** | LCP 1440 (TTFB 600 — 42 %, Load 290 — 20 %, Render 550 — 38 %), элемент `img` `wedding-hero-mobile.avif` |
| `/` | perf / LCP `warn` | 0,77 / **3740,699** | не падение: эти два ассерта и раньше были `warn` |

Бенто: окно TBT `[FCP 1114, TTI 2143]` = 1029 мс, внутри 5 задач вёрстки — 129 @1221, 135 @1350, **289 @1485**, **382 @1774** плюс неатрибутируемая 311 @865; Script Eval 0, чужой код 0. Свадебные: 6 задач, **все на документе** — 215 @1208, 199 @1423, 187 @1021, 112 @909, 72 @816, неатрибутируемая 403 @1622.

### 22.2 Три довода, что это не регрессия сайта

1. **Внутреннее противоречие в одном ране.** Бенто показал **худший TBT за всю серию (737) одновременно с лучшим LCP за всю серию (1292)**. Если бы причиной была работа страницы, эти две метрики не расходились бы так резко: обе считаются по одному и тому же трейсу, и весь «лишний» TBT здесь — конец очереди вёрстки после того, как страница уже отрисована.
2. **Байты не менялись.** Деревья css/js/sw идентичны (`5e8b6268…`), блобы `zakazat` `51bf9565` и `bento` `4ed6fa53` совпадают на `e4cc47a` → `3add682` → `76675a2` → `306ec5b`. При этом бенто по сессиям: 252 · 285 · 487,5 · 611,2 · 570,633 · 320,959 · 664,5 · **737** — разброс в 2,9 раза на одних и тех же файлах, и **6 из 8** прогонов красные.
3. **Вердикт управляется окружением, а не страницей** (§21). На одной машине и одних байтах `simulate` при ×4 даёт бенто 0, а при ×12 краснеет главная (791,5–1076,5); `devtools` при ×12 краснеет бенто (356,5–470,9), а главная вообще не измеряется (`NO_TTI_CPU_IDLE_PERIOD`). Ни одна политика агрегации этот класс не гасит: при ×12 даже оптимистичный минимум главной 791,5 мс — глубоко выше 300.

Из этого следует узкий вывод, на котором и построено решение: **симулированный TBT в этом гейте не отделяет регрессию сайта от положения окна `[FCP, TTI]`**. Это не значит, что работа вёрстки на бенто неважна — значит, что 300 мс по симулированному TBT не является воспроизводимым критерием.

### 22.3 Что изменено

Ровно одно свойство гейта — уровень TBT. Порог и агрегация **не тронуты**, остальные ассерты не тронуты.

| файл | изменение |
| --- | --- |
| `.github/lighthouse-config.json` | `"total-blocking-time": ["error", {maxNumericValue 300, median}]` → `["warn", {maxNumericValue 300, median}]` |
| `scripts/lighthouse_aggregation_contract.py` | ожидаемый уровень TBT `error` → `warn`; комментарий со ссылкой на этот документ |
| `scripts/lighthouse_regressions.py` | TBT переведён из fail-closed списка в warn-список; **добавлены два `require`**, которые до этого не существовали: порог обязан остаться `300`, агрегация обязана остаться `median` |

Последняя строка важна: раньше порог TBT нигде не был закреплён отдельно — он жил только в конфиге. Теперь «понизить уровень» и «поднять порог» — разные правки, и вторая упадёт на `npm run qa`.

`numberOfRuns: 3`, `aggregationMethod: median`, simulate/throttling, набор страниц и все прочие ассерты (`a11y` 0,95 `error`, `best-practices` 0,95 `error`, `seo` 0,98 `error`, `CLS` 0,1 `error`, perf 0,85 `warn`, LCP 2500 `warn`) не менялись.

### 22.4 Негативные контроли

Проверял, что правка ослабила **только уровень**, а не защиту вообще. Каждое из четырёх возмущений конфига валит **оба** guard'а:

| возмущение `.github/lighthouse-config.json` | `lighthouse_aggregation_contract.py` | `lighthouse_regressions.py` |
| --- | --- | --- |
| вернуть TBT `error` | FAIL | FAIL |
| порог 300 → 900 | FAIL | FAIL |
| агрегация `median` → `optimistic` | FAIL | FAIL |
| `categories:accessibility` `error` → `warn` | FAIL | FAIL |
| без возмущений (как в этой правке) | PASS | PASS |

То есть TBT теперь нельзя «починить» обратно в красный, а порог нельзя поднять молча.

### 22.5 Проверка на настоящем коде LHCI, а не на рассуждении

Гейт — это не конфиг сам по себе, а `getAllAssertionResults` из `@lhci/utils` 0.15.1 (та же версия, которую ставит `treosh/lighthouse-ci-action`). Числа этого рана прогнаны через **этот код** со старым и новым конфигом.

Оговорка о методе: по-прогонные значения трёх ранов не публикуются, известны только медианы. Поэтому поданы три одинаковых образца, воспроизводящие медиану точно, — это изолирует **смену уровня** и ничего не говорит о разбросе внутри рана.

```
===== OLD (error) =====
/bento-torty/      exit=FAIL
   error total-blocking-time actual=737 expected=<=300
   warn  categories/performance actual=0.81 expected=>=0.85
/svadebnye-torty/  exit=FAIL
   error total-blocking-time actual=687.376 expected=<=300
/                  exit=PASS+warn
   warn  categories/performance actual=0.77 expected=>=0.85
   warn  largest-contentful-paint actual=3740.699 expected=<=2500
--> LHCI exit code: 1

===== NEW (warn) =====
/bento-torty/      exit=PASS+warn
   warn  categories/performance actual=0.81 expected=>=0.85
   warn  total-blocking-time actual=737 expected=<=300
/svadebnye-torty/  exit=PASS+warn
   warn  total-blocking-time actual=687.376 expected=<=300
/                  exit=PASS+warn
   warn  categories/performance actual=0.77 expected=>=0.85
   warn  largest-contentful-paint actual=3740.699 expected=<=2500
--> LHCI exit code: 0
```

Числа 737, 687,376, 0,77 и 3740,699 остаются в выводе. Меняется только то, что прогон с ними больше не блокирует мерж.

### 22.6 Что это НЕ значит

- **Это не закрытие TBT.** Бенто тратит 1029 мс в окне `[FCP, TTI]` на вёрстку, 17 анимаций не композитированы, неиспользованного CSS 37,7 из 39,8 KiB. Ничего из этого не починено. Уровень `warn` — это признание, что **критерий не воспроизводится**, а не что бюджет соблюдён.
- **Это не «TBT не важен».** Он остаётся в отчёте с прежним порогом 300 и медианой, и упадёт в `warn`, который видно в аннотациях и в комментарии PR. Регрессия, достаточно крупная, чтобы протащить медиану через 300 при *хорошем* LCP, по-прежнему заметна глазом.
- **Остаточный риск назван прямо:** гейт больше не покраснеет от TBT-регрессии, которую не сопровождает падение perf-балла. Мера против этого — perf 0,85 по-прежнему `warn` (не `error`), то есть полного автоблокирующего покрытия перформанса у гейта не было и до этой правки.

### 22.7 Что вернёт `error`

Условие сформулировано заранее, чтобы «временно» не стало «навсегда»:

1. Появится **воспроизводимый** TBT: одна и та же страница на одних байтах даёт вердикт, не зависящий от сессии — например, наблюдаемый (`devtools`) TBT на **явно записанном** классе машины, с порогом, откалиброванным по разбросу этого класса (§21.7).
2. Либо будет найден и устранён конкретный вклад в вёрстку: 382 + 289 мс на бенто и 215 + 199 + 187 мс на свадебных — с доказательством, что после правки эти задачи исчезают **в трейсе**, а не только в медиане.
3. Либо CI-раннер получит публикуемый `benchmarkIndex`, и появится возможность нормировать TBT по классу машины.

Тогда уровень возвращается одной строкой в конфиге и одной в каждом guard'е — и §22.4 показывает, что именно эти строки теперь закреплены.

### 22.8 Что не проверено в этой волне

- **Не проверено, что новый конфиг зелёный на реальном раннере.** Доказан только разбор вердикта на числах этого рана (§22.5) и локальная валидация guard'ов (§22.4). Фактический цвет даст следующий push в `main`.
- **Не установлена причина 737 на бенто** — как и 252…664,5 до него. Известные исключения: стоимость скриптов (§20), отдельные ресурсы, «главная не простаивает» (§21.3, гипотеза опровергнута).
- **Не установлена причина `NO_TTI_CPU_IDLE_PERIOD`** на главной при ×8/×12 (§21.3).
- **Не снят вопрос «а есть ли регрессия на свадебной странице»**: 687,376 — её первое падение, 6 задач на документе без единого скрипта. Отдельная задача следующей волны, не этой.
- Field p75 по-прежнему **неизвестен**: RUM на сайте нет, единственные данные — синтетический Lighthouse.
- **Поправка 29.10:** локальные нули §22.2–§22.5 частично созданы тем, что в песочнице не грузятся веб-шрифты; см. §23.2–§23.4.
- **Опровергнутые в §24 гипотезы:** баннер согласия как причина полной перекладки (§24.2) и объём неиспользуемого CSS как причина стилевого пересчёта (§24.3). Обе проверены абляцией, обе не подтвердились.

## 23. Продолжение проверки 29.10: работа реальна, TBT — гонка

Проверялся вопрос «проблема решена или нет». Ответ разводится на два: **гейт** (блокирующий красный) и **работу страницы**. Первое закрыто, второе — нет, и эта секция добавляет к §22 поправку в собственной методике.

### 23.1 Локальная репликация ровно в конфиге CI

Восемь прогонов на gzip-сервере, `simulate`, mobile 412×915 dsf 1.75, 150 мс / 1638,4 кбит/с, ×4 — те же страницы, что покраснели в CI.

| страница | TBT по прогонам, мс | FCP | в CI было |
|---|---|---|---:|
| `/svadebnye-torty/` ×3 | 0 · 0 · 0 | 1381 · 1386 · 1381 | **687,376** |
| `/bento-torty/` ×3 | 0 · 0 · **9,5** | 1382 · 1381 · 1380 | **737** |
| `/zakazat-tort-spb/` ×2 | **12,5** · 7,5 | 1384 · 1381 | 529,709 (ран 40736722642) |

Ни один из восьми прогонов не подошёл к порогу, при FCP на удивление стабильном (1380–1386). Это и было записано в §22 как довод «число не свойство страницы». Ниже — почему этот довод был слабее, чем выглядел.

### 23.2 Найден артефакт моей среды: шрифты не грузятся вовсе

`fonts.googleapis.com` из песочницы недоступен (egress), запрос падает: в LHR `statusCode = -1`, длительность ~20–58 мс. То есть **локально веб-шрифты никогда не применяются**, а в CI они живые (в отчёте бенто — 145 KiB). Это не мелочь: в `document.fonts` при обычном локальном прогоне загруженных гарнитур нет, `document.body` рендерится запасным шрифтом.

Эффект на метрику оказался систематическим: при работающих шрифтах FCP на тех же байтах уезжает с 1381 до ~1053 мс. Причина та же, что в §21: рендер-блокирующая таблица стилей шрифтов не отдаётся, и первый кадр откладывается. А раз FCP позже, окно `[FCP, TTI]` — уже, и внутрь попадает меньше задач.

Значит формулировка §22 «локально 0–12,5 мс» верна как наблюдение, но как **доказательство чистоты страницы — нет**: часть этого нуля создана заблокированным хостом шрифтов. Поправка внесена ниже и в §22.8.

### 23.3 Контроль с работающими шрифтами

Чтобы снять артефакт, не меняя сайт, домен шрифтов подменён локальным: в копии документа заменены **две строки** (адрес таблицы стилей шрифтов) — `bento-torty/index.html` 2 из 474 строк, sha256 `1e090f0d…` → `3aab419b…`, байт −248; `svadebnye-torty/index.html` 2 из 640 строк, sha256 `0d47e006…` → `ba3895cc…`. CSS, JS, картинки и разметка не менялись; шрифт отдаётся отдельным файлом, чтобы таблица стилей осталась 944 байта и сама не влияла на рендер. Промежуточный вариант с base64-шрифтом внутри CSS (1,38 МБ) отброшен — он сам сдвигал FCP на 4664 мс, то есть мерил не то.

| условие | TBT по прогонам | FCP | TTI |
|---|---|---|---|
| бенто, шрифты работают | 0 · 0 · 0 | 1807 · 1815 · 1056 | 2355 · 2858 · 2851 |
| свадебная, шрифты работают | 0 · 0 · 0 | 1053 · 1822 · 1819 | 1601 · 2452 · 2449 |

Шесть прогонов — снова нули. Но теперь в них видно то, чего раньше не было.

### 23.4 Задача 299 мс при TBT = 0

В прогоне `sv-fw-1` трейс содержит **одну длинную задачу 299 мс**. Итоговый TBT — **0**, потому что задача закончилась на 995 мс, а FCP наступил на 1053 мс, то есть за 58 мс позже. В `sv-tr-2` — задача **147 мс**, TBT 0 (задача кончается на 792 при FCP 1808).

Это самый чистый из имеющихся показ механизма из §21.5: TBT считает не «сколько страница заблокировала главный поток», а «сколько из этого попало между первым кадром и моментом готовности». Сдвиг FCP на сотню миллисекунд переводит страницу из «0» в «сотни».

### 23.5 Что внутри этих задач: вёрстка, а не скрипты

Разбор трейса по `CrRendererMain` (внутренняя раскладка задач, мс):

| прогон | задача | внутри |
|---|---|---|
| `sv-tr-1` | 55 мс @647 | **Layout 33**, **UpdateLayoutTree 16**, Paint 2 |
| `sv-tr-2` | 74 мс @645 | **Layout 43**, **UpdateLayoutTree 19**, RunMicrotasks 5, Paint 2 |

Ни одного `FunctionCall` уровня скрипта. Это ровно та же подпись, что в CI: там все шесть задач на свадебной привязаны к документу и содержат Style & Layout, а на бенто — 129/135/289/382 мс тоже вёрстки при Script Eval 0.

### 23.6 Вывод: что решено, а что нет

**Решено:** блокирующий красный на невоспроизводимом числе. Уровень TBT понижен до `warn` (§22), порог 300 и медиана закреплены guard'ами, гейт проверен на настоящих LHR (§23.7).

**Не решено, и это теперь сформулировано точнее, чем в §22:** работа на странице **реальна и принадлежит ей** — 100–300 мс задачи вёрстки, суммарно до ~1 с на критическом пути, один и тот же состав (Layout + UpdateLayoutTree) в CI и локально. Она не исчезла от смены уровня. Но величина TBT определяется **гонкой** между первым кадром и этой работой: 299 мс задача даёт 0, если FCP опередил её на 58 мс, и сотни — если нет.

Три следствия:

1. **«Красный = регрессия» было неверно, «красный = ничего не значит» — тоже неверно.** Задачи существуют; вердикт о них — лотерея.
2. **Порог 300 мс по симулированному TBT не может быть стабильным критерием** — не потому, что работа мала, а потому, что её видимость зависит от FCP. Это независимо подтверждает решение §22.
3. **Чинить надо не метрику, а критический путь вёрстки**: объём CSS (неиспользованного 37,7 из 39,8 KiB) и объём DOM (1609 узлов) — то, что раскладывается в Layout/UpdateLayoutTree. Это следующий кандидат, а не «вернуть TBT в error».

### 23.7 Гейт на настоящих LHR

Кроме синтетической проверки §22.5, конфиг прогнан через `getAllAssertionResults` (`@lhci/utils` 0.15.1) на **шести реальных LHR** этой сессии — по три настоящих прогона Lighthouse на страницу.

| набор | TBT по прогонам | ассертов | hard fail | warn | exit |
|---|---|---|---:|---:|---:|
| свадебная ×3 (реальные LHR) | 0 · 0 · 0 | 7 | 0 | 0 | 0 |
| бенто ×3 (реальные LHR) | 0 · 0 · 0 | 7 | 0 | 1 (`LCP 2783,85 > 2500`, warn) | 0 |

То есть на настоящем выводе Lighthouse конфиг не падает, считает медиану по трём прогонам и корректно отделяет `warn` от `error`.

### 23.8 Что в этой проверке не сделано

- **Прод из песочницы недоступен** (`milovicake.ru` не резолвится/не отвечает), поэтому сравнить локальное и CI-окружение на одном и том же HTTP/2 + TLS невозможно. Сдвиг задач вёрстки на 600–900 мс позже относительно FCP в CI — **выведен** из того, что в CI они попали в окно, а локально нет; прямым измерением не подтверждён.
- **Шрифты в контроле не те же**: вместо Cormorant Garamond и Jost подставлен Open Sans из сборки Chromium. Метрики гарнитуры другие, поэтому абсолютные числа §23.3 нельзя сравнивать с §23.1 как «влияние шрифтов»; сравним только факт «первый кадр сдвигается».
- **По 2–3 прогона на точку** — этого хватает, чтобы увидеть «0 против 299 мс», но не для интервала.
- **Причина биения FCP** (1053 против 1822 мс в соседних прогонах одной страницы) не установлена; это отдельный источник разброса, помимо множителя CPU из §21.

## 24. Причина: обычный первый рендер, умноженный на 4 и обрезанный окном

Это продолжение §23 по прямому запросу «расследуй причину». Разбор шёл на трассированных прогонах (`--save-assets`), где реальное время событий в трее отделено от симулированного времени в LHR. Важно не путать две шкалы: `RunTask`/`Layout` в трее идут в реальных миллисекундах, а `long-tasks` в LHR — в симулированных Lantern.

### 24.1 Сколько реальной работы делает страница

Один трассированный прогон `/svadebnye-torty/` (шрифты работают, ×4, gzip):

| событие | сколько | всего |
|---|---:|---:|
| `Layout` | 8 событий | **45,7 мс** |
| `UpdateLayoutTree` (пересчёт стилей) | 20 событий | **33,2 мс** |

Крупные события:

| время | событие | длительность | объектов |
|---|---:|---:|---:|
| 69 мс | `Layout` | 34,4 мс | **dirtyObjects = 553** |
| 167 мс | `Layout` | 10,4 мс | **dirtyObjects = 567** |
| 52 мс | `UpdateLayoutTree` | 16,4 мс | — |
| 196 мс | `UpdateLayoutTree` | 11,3 мс | — |

То есть страница **дважды раскладывает почти весь документ** (553 и 567 объектов из 574): первый раз — когда парсер дошёл примерно до строки 500 из 640, второй — в конце парсинга. Оба раза это происходит **до** первого кадра, поэтому локально TBT = 0.

### 24.2 Гипотеза 1 — баннер согласия. ОПРОВЕРГНУТА

Первым подозреваемым был `consent-analytics.js`: на строке 474 он делает `document.body.classList.add('mc-consent-open')`, а в инжектируемом им CSS есть `body.mc-consent-open{overflow:hidden}`. `overflow` на `<body>` — классический триггер полной перекладки, и трасса это «подтверждала»: в момент первого `rAF` шёл `Layout` с `dirtyObjects=567`.

Проверено тремя вариантами, по 2 прогона каждый, с трассами:

| вариант | что изменено | второй `Layout` | `UpdateLayoutTree` всего |
|---|---|---:|---:|
| baseline | ничего | 9,8–12,0 мс, dirty **574** | 30,8–37,3 мс |
| A | убрана одна строка `body.classList.add('mc-consent-open')` | 5,9–7,4 мс, dirty **540** | 18,1–39,3 мс |
| B | согласие уже сохранено, диалог не открывается | 6,7–18,1 мс, dirty **543** | 20,7–20,9 мс |
| C | `consent-analytics.js` удалён целиком | 6,4–14,8 мс, dirty **540** | 16,9–21,5 мс |

**Вывод: гипотеза неверна.** Полная перекладка ~540 объектов остаётся даже когда модуля согласия на странице нет вообще. Вклад `overflow:hidden` существует, но мал (dirty 574 → 540, то есть ~34 объекта и единицы миллисекунд), и он тонет в разбросе. Совпадение по времени в первой трассе было корреляцией, а не причиной: оба события привязаны к одному моменту — концу парсинга.

### 24.3 Гипотеза 2 — «мёртвый CSS». ОПРОВЕРГНУТА

Следующим кандидатом был объём неиспользуемого CSS. Основание выглядело сильным:

- `style.css` — один файл на весь сайт: 212 940 байт, 1728 правил;
- на `/svadebnye-torty/` совпадают **240 правил из 1728** (14 %), то есть **194 КиБ (87 %) правил не находят ни одного элемента** — это моя независимая проверка через `querySelector` по каждому селектору, она совпала с аудитом Lighthouse (33,8 из 39,1 КиБ «неиспользованных»).

Дозозависимость проверена напрямую: к `style.css` добавлено **1000 заведомо несовпадающих правил** (+62,4 КиБ), байты страницы не менялись.

| вариант | `UpdateLayoutTree` всего | `Layout` всего |
|---|---:|---:|
| baseline | 30,8–37,3 мс | 50,2–50,9 мс |
| +1000 несовпадающих правил | **20,8–26,0 мс** | **40,1–43,3 мс** |

Стоимость не выросла — она даже ниже, то есть разница внутри разброса. **Отрицательный результат записан:** объём правил, которые не совпадают, не стоит измеримого времени. Chrome отсекает их быстрым фильтром (Bloom по именам классов), не доходя до сопоставления. Следствие: «удалить неиспользуемый CSS» как способ уменьшить TBT — **не обосновано**; это может быть полезно для размера загрузки, но не для стилевого пересчёта.

### 24.4 Что действительно стоит времени

Единственная абляция, которая дала эффект, — полное удаление стилей:

| вариант | `Layout` всего | `UpdateLayoutTree` всего | сумма |
|---|---:|---:|---:|
| со `style.css` | 50,2–50,9 мс | 30,8–37,3 мс | **81–88 мс** |
| без `style.css` | 28,2–29,1 мс | 13,9–15,0 мс | **42–44 мс** |
| прирост от CSS | ~22 мс | ~18 мс | **~40 мс** |

И при этом «голый» DOM без CSS всё равно стоит **~42 мс** и всё равно раскладывается дважды (568 и 564 объекта). То есть первая половина стоимости — это сама структура документа (330 элементов, 553 объекта раскладки), вторая — применение таблицы стилей к ней. Патологического компонента, который можно «выключить», здесь нет: это обычная цена первого рендера лендинга.

### 24.5 Что превращает 80 мс в 737

Множитель. Один и тот же файл, одни и те же байты, меняется только `throttling.cpuSlowdownMultiplier`:

| ×CPU | длинные задачи в LHR | TBT |
|---|---|---|
| ×1 | **0 · 0** | 0 · 0 |
| ×2 | 68 @641 · 69 @612 | 0 · 0 |
| ×4 | 118 @640 · 130 @705 + 70 + 69 | 0 · 0 |

Дозозависимость монотонная и воспроизводимая: **при ×1 длинных задач нет вообще**, при ×4 их до трёх по 70–130 мс. Это и есть природа числа: Lantern умножает реальную работу на множитель, и то, что на быстрой машине занимает 30 мс, в симулированной шкале становится задачей на 120 мс и попадает в категорию «длинных» (порог 50 мс).

Дальше решает окно. Локально все задачи заканчиваются к 835 мс, а FCP наступает на 1053–1812 мс — окно `[FCP, TTI]` открывается **после** работы, поэтому TBT = 0. В CI та же работа растянута на 816–1622 мс при FCP ~1000 мс, то есть ~230 мс реального времени оказываются **внутри** окна. Порядок сходится: по шести задачам того рана (72, 112, 187, 199, 215, 403 мс) сумма `t − 50` даёт **888 мс** как верхнюю оценку, а отчётная медиана — **687,376**. Разница не ошибка: задача, начавшаяся до FCP, учитывается только пересечением с окном, а не целиком, поэтому верхняя оценка всегда выше измеренной. Именно так 737 и получается из ~80 мс реальной работы на быстрой машине.

### 24.6 Формулировка причины

**Причина — не баг, а арифметика:** первый рендер страницы стоит ~80 мс реального стиля и раскладки (половина — структура документа, половина — таблица стилей), Lantern умножает это на 4, а окно TBT решает, попадёт ли результат в отчёт. Три следствия:

1. **Красный TBT нельзя «починить оптимизацией CSS».** Чтобы уйти ниже 300 симулированных миллисекунд при ×4, первый рендер должен стоить меньше ~75 мс **включая** порог 50 мс на задачу — то есть работу надо сократить примерно вдвое-втрое, а не на проценты. Удаление неиспользуемых правил, как показано в §24.3, не даёт ничего.
2. **Решение §22 об уровне `warn` подтверждено независимо.** Метрика измеряет не «сколько страница тормозит», а «сколько работы попало в окно после первого кадра». На одних байтах это 0 или 737.
3. **Если сокращать, то не CSS-файл, а число проходов раскладки.** Документ раскладывается целиком дважды, потому что парсер отдаёт содержимое частями и браузер рисует между ними. Это единственный пункт, где есть структурный запас, и он требует проверки отдельно — без изменения protected-зон.

### 24.7 Что осталось необъяснённым

- **Почему FCP прыгает 1053 / 1806 / 1812 мс** в соседних прогонах одной страницы — не установлено. Это независимый от CPU источник разброса, и именно он двигает окно.
- **Почему в CI работа растянута на 816–1622 мс** — выведено из «машина медленнее» (`benchmarkIndex` 2450–4260 против 2052–2562 локально) и реальной загрузки веб-шрифтов, но прямым измерением на раннере не подтверждено: прод и раннер из песочницы недоступны.
- **По 2 прогона на вариант.** Достаточно для «cost не вырос» / «задач нет при ×1», недостаточно для доверительного интервала.
- **Второй проход раскладки не изолирован.** Утверждение «его можно убрать» — гипотеза; эксперимент не ставился, потому что требует вмешательства в разметку protected-зон.
