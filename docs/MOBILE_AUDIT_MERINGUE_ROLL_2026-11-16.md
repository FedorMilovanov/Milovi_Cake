# Мобильный аудит `/meringue-roll/` — что улучшили и что упустили

Дата: 2026-11-16 · Ветка: `arena/bdcf9e2b-milovi-cake` (от `main` = `b5ad1b1`) · Предмет: `meringue-roll/index.html` (142 385 Б)

## 0. Короткий ответ

**Улучшили — но не всё и не то, что заметно на телефоне.**

Страница действительно стала заметно крепче там, где раньше ломалась на мобильных:
safe-area, отсутствие CLS от фото, поведение без JS, загрузчик, темы. Это видно по коду и
закрыто тестами.

Но **мобильная оболочка сайта к этой странице так и не была подключена**: `/meringue-roll/` —
единственная страница сайта, которая грузит `js/nav.js`, но не грузит `css/style.css`, а
единственный источник токенов `--mc-nav-*` живёт именно в `style.css`. Из-за этого нижний бар
теряет привязку к низу экрана, шторка «Ещё» — свой якорь, а сама страница ещё и платит
~60 КБ за декоративную иконку 30×30 и не имеет ни одного `srcset`.

## 1. Методика и ограничения

- Разбор статики: HTML, 5 инлайновых `<style>` (65 517 Б CSS), 11 инлайновых `<script>`
  (16 267 Б JS), 6 внешних CSS, `js/nav.js`, `css/v20-fixes.css`, `css/final-fixes.css`,
  `css/premium-overrides.css`, `css/v20-dark-and-fixes.css`, `js/consent-analytics.js`.
- Каскад проверялся по правилам CSS Custom Properties: **неразрешённый `var()` без
  фолбэка делает объявление недействительным при вычислении значения** — свойство ведёт себя
  как `unset`, даже если объявление помечено `!important`. Дальше — арифметика, без браузера.
- Браузеров в песочнице нет, поэтому геометрия выведена статически, а затем проверена
  в CI новым гардом `tests/mobile-shell.spec.js` (Chromium, 412×915 — проект
  `chromium-mobile`). Гипотеза подтверждена в живом браузере: если погасить токены на
  загруженной странице (`:root{--mc-nav-*:initial}`), вычисленный `bottom` бара равен
  **−9989,05 px** — то есть бар стоит на статической позиции в конце документа. С
  объявленными токенами `bottom` = 8 px, бар прижат к нижней кромке. Этот негативный
  контроль остался в спеке.
- Что **не** проверялось: реальные метрики Lighthouse для этой страницы (лейн меряет `/`,
  `/gallery/`, `/prigorody/gatchina/`, `/svadebnye-torty/`, `/privacy/`), Core Web Vitals на
  живом 4G, визуальный дифф на устройствах.

## 3. Дефекты

### P0 — нижний бар не привязан к низу экрана (исправлено)

`/meringue-roll/` — единственная страница, которая подключает `js/nav.js` и не подключает
`css/style.css` (проверены все 34 отслеживаемых `index.html`). Токены объявлены только там:

```
css/style.css:1  :root{ … --mc-safe-b; --mc-nav-side:12px; --mc-nav-gap:8px;
                        --mc-nav-h:60px; --mc-nav-total:calc(...) … }
```

А геометрию бара задают переопределения — **без фолбэков и с `!important`**:

```
css/v20-fixes.css:570-572   .mc-nav{ left:var(--mc-nav-side)!important;
                                     right:var(--mc-nav-side)!important;
                                     bottom:var(--mc-nav-gap)!important; }
css/final-fixes.css:490     #mcNav.mc-nav{ height:calc(var(--mc-nav-h) + var(--mc-safe-b))!important;
                                            padding:0 5px var(--mc-safe-b)!important; }
css/v20-fixes.css:586       body.has-mc-nav{ padding-bottom:calc(var(--mc-nav-total) + 16px)!important; }
js/nav.js:202               .mc-sheet{ bottom:var(--mc-nav-total); }
```

Фолбэки есть только в собственной вставке `nav.js` (`left:var(--mc-nav-side,12px)`,
`bottom:var(--mc-nav-gap,8px)`, `js/nav.js:113-114`), но `!important`-объявления из
`v20-fixes.css` выигрывают каскад и, оставшись без значения, дают `left/right/bottom: auto`.
Для `position:fixed` это значит «встать по статической позиции в потоке» — то есть в конце
документа, а не у нижней кромки.

**Сделано:** в `:root` страницы добавлены ровно те же токены, что в `style.css`
(`--mc-safe-b`, `--mc-nav-side`, `--mc-nav-gap`, `--mc-nav-h`, `--mc-nav-total`), с
комментарием, откуда они и почему обязаны совпадать. Правка не меняет внешний вид ни на
одном другом элементе: все остальные правила, читающие эти токены, относятся к узлам,
которых на странице нет (`.calc-right-col`, `.back-to-top`, `.back-to-…`), либо к
`.mc-nav`/`.mc-sheet`, для которых это и есть исправление.

**Подтверждено в браузере (CI, chromium-mobile):** до правки эквивалентное состояние
(погашенные токены) даёт `bottom: -9989,05px` — бар уезжает на ~10 000 px ниже экрана,
то есть на телефоне его просто нет. После правки `bottom` = 8 px, бар стоит у нижней
кромки; на `/meringue-roll/` гард зелёный.

**Гард:** `tests/mobile-shell.spec.js` — на `/`, `/meringue-roll/` и `/prigorody/gatchina/`
проверяет, что токены объявлены, бар виден после первой прокрутки (`body.mc-nav-veiled`
снимается, как у живого пользователя), прижат к низу экрана (зазор `--mc-nav-gap` + допуск
24 px), не ниже 48 px по высоте и не вылезает за края; на десктопе — что бар не строится
(`nav.js` создаёт его только при `innerWidth <= 768`). Плюс негативный контроль механизма:
без токенов бар обязан уехать за пределы экрана.

### P1 — мобильная CTA-кнопка в разметке есть, на экране её быть не может

```
css/premium-overrides.css:12-17   (верхний уровень, без условий)
   .mobile-sticky-cta, #mobileStickyWa{display:none!important;visibility:hidden!important;
                                      pointer-events:none!important}
css/v20-fixes.css:558-563         @media (max-width:768px){ то же самое }
```

Страница при этом продолжает возить саму кнопку (`meringue-roll/index.html:1940`), её CSS
(`1498-1511`) и JS, который переключает `style.display` и `.visible`. Это не «выключенная на
время» кнопка: селектор по `id` + `!important` в двух файлах, отменить их страница не может.

Политика сайта с r26 — «одна постоянная нижняя навигация» (та самая, что строит `nav.js`;
центральная золотая кнопка ведёт в WhatsApp), поэтому скрытие CTA — осознанное решение, и
дефект здесь не «кнопку спрятали», а «кнопку оставили мёртвым кодом и под неё подогнали
отступы»:

- `.back-top` на ≤768px стоит на `bottom: calc(76px + env(safe-area-inset-bottom))`
  (`meringue-roll/index.html:1678`) с комментарием «выше bottom-nav» — 76 px это место под
  CTA, а не под бар (бар — 60 px + 8 px зазор + safe-area);
- из-за этого «кнопка наверх» висит на ~8 px выше, чем нужно, и это единственное, что
  осталось от CTA.

**Решение (нужно ваше):** либо убрать разметку/CSS/JS CTA как мёртвый код и привязать
`.back-top` к `calc(var(--mc-nav-total) + var(--mc-btt-gap))`, либо, наоборот, оставить
кнопку как продуктовое решение — тогда её нужно снимать из-под глобальных правил точечно
(скоуп по классу страницы), а не бороться `!important`. Сейчас в коде оставлен комментарий,
что логика рабочая, и CTA не удалён.

Сопутствующее наблюдение: пересечение `.mobile-sticky-cta` (right 16, z 90) и `.back-top`
(right 20, z 100) в одной точке — **не баг этой страницы**, потому что CTA не отображается;
как только CTA включат обратно, пересечение появится сразу.

### P1 — декоративная иконка 30×30 весит 61 КБ (исправлено)

`img/icon-loading.webp` — это **1024×1536**, 61 514 Б (заголовок VP8: `0x0400 × 0x0600`).
На странице она стоит в карточке «Ручная работа» с `width="30" height="30"`,
`object-fit:cover`, `opacity:.85` и **без** `loading` — то есть грузилась сразу, вне
`lazy`-политики остальных фото.

**Сделано:** `img/meringue_feature_handwork.webp` — 96×144 (тот же кадр и то же соотношение
сторон, значит `object-fit:cover` даёт ровно ту же картинку в кружке), WebP q82, **1 654 Б**
(−97,3 %), плюс `loading="lazy"`. Файл `icon-loading.webp` не тронут: он же используется на
`/call/` в размере `min(60vw,280px)`.

### P2 — адаптивных картинок нет ни одной

11 `<picture>`, 13 `<img>`, **0** `srcset`, **0** `sizes`: каждая картинка — один файл
59–101 КБ, который на 390-пиксельном экране растягивается/ужимается CSS. Суммарный вес всех
изображений, на которые ссылается страница: 860 122 Б (WebP) / 776 959 Б (AVIF).
Для сравнения, на `/svadebnye-torty/` схема `srcset` есть и проверяется тестами
(`-sm`/full варианты, бюджеты байт в `tests/landing-smoke.spec.js:640-671`) — то есть
приём в проекте известен, к этой странице не применён.

Важная деталь на будущее: на телефоне с DPR ≈ 2,6 (Pixel 7) браузер при `sizes="90vw"` всё
равно выберет вариант ~960 px, поэтому выигрыш даёт не сам `srcset`, а сознательное решение
«отдаём 1,5× вместо 2,6×». Это вопрос к владельцу, а не техническая правка.

### P2 — состояние плавающих элементов не считалось при загрузке (исправлено)

`.back-top` получала класс `.show` только из обработчика `scroll`, полоса прогресса — тоже.
После перезагрузки на восстановленной позиции и при переходе по якорю (`#faq`, `#order`,
`?city=pushkin`) событие `scroll` не приходит: страница уже прокручена, «наверх» не видно,
прогресс стоит на нуле, пока пользователь не тронет экран. Исправлено: у `syncBackTop` и
`syncFloating` появился немедленный вызов на старте (+ `resize` для прогресса — высота
документа меняется при повороте экрана).

### P3 — обращения к DOM без проверки (исправлено)

`const hdr = document.getElementById('siteHdr')` и `const btn = document.getElementById('backTop')`
использовались в обработчике `scroll` без проверки на `null`: любой вариант страницы без этих
узлов (A/B, сокращённая разметка, ошибка сборки) давал бы исключение на каждом событии
прокрутки. Обёрнуто в `if`.

## 4. Что я перепроверил и снял как «не дефект»

- `#mrScrollProgress` — не мёртвый узел: позиционирование и градиент заданы инлайн-стилем в
  разметке, JS двигает `width`. Полоса работает, дефекта нет.
- Повторные `meringue_roll_5.webp` / `_6.webp` / `meringue_box_nobg.webp` в разметке — это
  повторные ссылки на один URL, браузер берёт их из кеша: двойной загрузки нет.
- Пересечение `.mobile-sticky-cta` и `.back-top` — не наблюдается, пока CTA скрыт (см. P1),
  но станет реальным, как только CTA включат.
- `100vh` (3 вхождения) против `dvh` (3 вхождения) — на этой странице `vh` используется в
  секциях, где переполнение не критично, а `dvh` уже стоит в мобильных правилах; замену
  делать не стал, чтобы не трогать геометрию без визуальной проверки.

## 5. Почему это упустили (процесс, а не код)

1. **Ни один тест не проверял мобильную оболочку на этой странице.** `tests/mobile-menu.spec.js`
   ходит на `/meringue-roll/` только чтобы найти ссылку в меню; `tests/layout-matrix.spec.js`
   проверяет `#mcNav` на `/` (где `style.css` подключён) в 10 ширинах и 2 темах.
   Страница без базового CSS не попадала ни в один геометрический тест — теперь попадает.
2. **Мёртвый CTA никто не заметил**, потому что скрытие живёт в переопределениях, а не в
   разметке страницы: читая страницу, видишь рабочую кнопку, читая сайт — видишь политику
   «один бар». Разъезд виден только при сравнении двух файлов.
3. **Бюджетов на декоративные иконки нет**: бюджеты байт есть для картинок каталога
   (`landing-smoke.spec.js:645`) и для страниц Lighthouse (`lighthouse_regressions.py`), но
   правило «`<img>` 30×30 не может весить 61 КБ» нигде не сформулировано.
4. **Lighthouse-лейн не меряет эту страницу.** `/meringue-roll/` — самая «мобильная» по
   формату страница (вертикальный десерт, один товар, WhatsApp-воронка), но в бюджетном
   контуре её нет.
