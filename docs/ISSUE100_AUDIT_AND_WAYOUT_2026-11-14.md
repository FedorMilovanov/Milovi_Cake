# Issue #100 — аудит причин и проверенный выход (2026-11-14)

**Статус:** кандидат реализован и локально проверен, **в git — локальные коммиты, push НЕ выполнялся**.
Issue #100 остаётся **OPEN** до полной CI-верификации (см. §6). Метрические пороги
LCP ≤2500 мс / TBT ≤300 мс **не ослаблялись**.

---

## 1. Резюме для владельца

1. **Причина найдена и подтверждена новыми экспериментами.** Mobile LCP упирается не в
   загрузку CSS/картинок, а в **стоимость первого полного Style+Layout огромного DOM
   (≈1600 элементов) до первой отрисовки** — «element render delay». Это согласуется со
   всеми трассами исследования (первый Layout 534–667 мс на CPU×4, «significant initial
   offscreen layout cost»), но теперь доказано *решающими* контрольными пробами.
2. **Текущее «направление следующей работы» (critical CSS) не закрывает бюджет.**
   Проба с полным инлайном всего CSS (удаление сети CSS целиком) дала **−27 мс** LCP
   на главной и **+250 мс** на Гатчине; откладывание CSS без инлайна — «−75 мс LCP,
   +1000 мс TBT, CLS 0.33». Цепочка CSS-загрузки — **не** ограничивающий фактор LCP.
   Critical CSS остаётся полезной оптимизацией FCP, но как «выход из #100» — тупик.
3. **Выход найден: детерминированный пропуск offscreen-layout на первом кадре.**
   Нативный A/B (Chrome, CPU×4, сеть 150 мс / 1.6 Mbps — методология самой лаборатории
   issue): **главная −606 мс LCP по медиане пар (4/4 пары лучше), Гатчина −638 мс (4/4)**.
   CLS 0, финальная геометрия и пиксели идентичны базе, TBT-прокси не хуже (longtask-сумма
   −74…−458 мс). Это воспроизводит и превосходит лучший предыдущий эксперимент
   (−452/−324 мс, transient content-visibility), **исправляя его единственный дефект —
   недетерминированное восстановление**.
4. **Что сделано локально:** механизм встроен в исходники всех страниц с `<main>`
   (15 файлов + шаблон пригородов, 14 сгенерированных страниц), инжектор идемпотентный,
   все контракты `npm run audit:*`, `build:pages`, `audit:pages` — **PASS**. Браузерная
   верификация: engagement/снятие класса, пиксельный паритет 8/8, якорь #catalog при
   клике в окне пропуска приземляется идентично базе (y=1940 во всех прогонах),
   no-JS и старые браузеры — безопасный обычный рендеринг.

## 2. Причинная модель LCP/TBT (что доказано чем)

Модель подтверждена разбором LHR + новыми пробами на собранном Pages-артефакте
(`_site` = production-байты, Lighthouse 13.6 mobile simulated):

```
sim LCP ≈ sim FCP (сеть: HTML→CSS→шрифты→hero, ~1350 мс локально / ~2000 мс на CI)
        + масштабированный observed render delay (style+layout+decode+paint)
```

| Гипотеза (из истории #100) | Новая решающая проверка | Результат |
|---|---|---|
| «LCP держит цепочка render-blocking CSS (6 файлов, 74 KB)» | **Проба E**: весь CSS инлайном в `<style>`, сетевых CSS-запросов нет | LCP **−27 мс** главная / **+250 мс** Гатчина. Цепочка CSS — не ограничитель LCP |
| «Critical CSS (v4) — основной выход» | Проба B (defer всего CSS) + оценка v4 из истории (−203 мс) | FCP улучшается (−410 мс), LCP почти не двигается; TBT **+760…+1000 мс** (шторм restyle при переключении media), CLS 0.33. **TBT-гейт заваливается** |
| «Offscreen Layout дорогой; пропуск на первом кадре ускоряет рисунок» (transient CV, отклонён из-за недетерминированности) | **Нативный A/B CPU×4×сеть**: детерминированный пропуск (снятие класса через 2 кадра после FCP + резервные пути) | **−606 / −638 мс LCP медиана пар, 4/4 обеих страниц; CLS 0; геометрия идентична** |
| «TBT-хвосты: nav.js storm 177–215 мс, snapSectionHeight 390 мс forced layout» | Longtask-сумма после FCP в нативном A/B | Пропуск сам по себе даёт −74…−458 мс longtask-суммы; точечные фиксы nav.js/main.js — см. §7 |

### 2.1. Почему хвосты «во всех прогонах» недостижимы микрооптимизациями

Разброс LCP на одном и том же SHA в CI (2359–3126 мс) — шум shared-runner CPU, а не
код. При медиане ≈2300–2700 хвосты будут стабильно пересекать 2500. Для критерия
«≤2500 в **каждом** холодном прогоне» медиана должна опуститься до ≈1900–2100.
Измеренный выигрыш пропуска (−600+ мс в CPU-ограниченном режиме) — первый рычаг
достаточной величины за всю историю вопроса.

### 2.2. Наблюдения по маршрутам

- **Главная:** LCP = hero-изображение (preloaded AVIF, 18 KB — сеть мала); render delay
  доминирует; DOM 1603 элемента; Style & Layout 0.78–1.0 с observed.
- **Гатчина:** тот же hero-узел; страница выше (14,5–17,9k px), симулированный LCP
  бимодален (±217 мс) — это шум модели, не эффект кода (виден одинаково в обеих руках).
- **Галерея/свадебная:** TBT-хвосты — отдельная ветка работ (§7).

## 3. Что именно реализовано (кандидат)

Сниппет `[P100]` в `<head>` каждой страницы с `<main>` (маркер-комментарий, стиль и
скрипт). Механизм:

1. Парсер, до первого layout, добавляет `mc-fast-init` на `<html>`.
2. Пока класс активен: `main > *:not(#home):not(.section-fade-divider)` получает
   `content-visibility:auto; contain-intrinsic-size:auto 1000px` — offscreen-секции
   (каталог, начинки, отзывы, калькулятор, SEO-блоки) **не участвуют в первом
   Style+Layout**. Hero и первый экран — нетронуты (protected hero не затронут).
3. Снятие класса — детерминированно, 4 независимых пути:
   - 2 кадра после записи `first-contentful-paint` (PerformanceObserver) — пропуск
     ровно до первого кадра, восстановление сразу после рисунка hero;
   - `load` + 2 кадра (страховка);
   - жёсткий `setTimeout(rm, 1500)` — класс **не может** «застрять» (деградация
     предыдущего эксперимента исключена конструктивно);
   - первое взаимодействие (`pointerdown/keydown/wheel/touchstart`, capture) —
     восстановление до обработки жеста.
4. После снятия класса документ раскладывается **точно как раньше** — `contain-intrinsic-size`
   влияет только на окно ≤1500 мс, финальная геометрия побайтно совпадает с базовой.

**Отказоустойчивость:**
- без JavaScript класс не добавляется → обычный рендеринг (проверено: hero и контент видны);
- браузеры без `content-visibility` игнорируют правило → обычный рендеринг;
- исключения в скрипте → `rm()` в fallback-путях;
- SEO: контент остаётся в HTML/индексируемом DOM; `content-visibility` действует лишь
  ≤1.5 с после загрузки (в отличие от постоянных вариантов, запрещённых в r67).

Изменённые файлы: `index.html`, 12 контент-страниц, `prigorody/index.html`,
`prigorody/_template.html` (+14 перегенерированных страниц пригородов);
`scripts/inject_fastinit_snippet.py` — идемпотентный инжектор (маркер-контракт).

Почему simulated-выигрыш локально меньше нативного: CPU песочницы быстрый, доля layout
в LCP мала. На CI-runner'ах и реальных мобильных CPU доля layout близка к условиям
CPU×4 — там ожидается выигрыш, близкий к нативным −606/−638 мс. Это же объясняет,
почему все прошлые CSS-гипотезы «не двигали» симуляцию.

## 5. Негативные результаты этой волны (не тратить время повторно)

1. **Defer 6 CSS-таблиц** (проба B): LCP ≈0, TBT +760…+1000 мс, CLS 0.33. Не отгружать.
2. **Весь CSS инлайном** (проба E, верхняя граница «CSS-сети»): LCP −27/+250 мс.
   Критический CSS как единственный рычаг LCP — **тупик**; пересмотреть приоритет v4.

   (−39…−124 мс против −606 мс в CPU-режиме). Выводы по layout-оптимизациям принимать
   только по CPU-троттлингу (CDP CPU×4), как и было принято в лаборатории issue.
