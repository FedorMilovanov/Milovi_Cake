# Style & Layout: мертвый CSS или анимации (2026-11-03)

## Вопрос

После выноса курсивных начертаний (`docs/FONT_DELIVERY_2026-11-02.md`) остался
вопрос, откуда берутся 1432 мс `Style & Layout` и 59% «неиспользуемого»
`css/style.css`. Гипотеза была такая: CSS слишком много, надо вычистить мёртвое.

**Гипотеза не подтвердилась.** Мёртвого CSS в буквальном смысле нет, а стоимость
`Style & Layout` давали две бесконечные анимации, которые каждый кадр
инвалидировали стили и раскладку без всякой пользы для внешнего вида.

Ниже — обе части, с числами и с тем, что именно они **не** доказывают.

---

## Часть 1. Сколько CSS реально можно снять

### Как считалось

Правила брались из CSSOM семи runtime-файлов (9 CSS-файлов минус два файла
шрифтов), затем проверялись тремя независимыми способами:

1. **Статический DOM.** Для каждого селектора — `document.querySelector` на всех
   33 страницах сайта (обход дерева, включая `prigorody/<city>/`).
2. **Реальное использование.** CDP `CSS.startRuleUsageTracking` в 80 прогонах:
   33 страницы × 2 темы (desktop) + 7 страниц × 2 темы (mobile), с прокруткой и
   интеракциями — корзина, калькулятор, лайтбокс, галерея-фильтры, тема, меню.
3. **Упоминания в репозитории.** Поиск каждого класса/идентификатора по всем
   отслеживаемым файлам (HTML, JS, CSS, скрипты, тесты, документация).

Селекторы нормализовались: убирались `:hover`, `:focus-visible`, `::before` и
подобные. Первая версия нормализации была **с дефектом** — `:focus` стоял в
регулярном выражении раньше `:focus-visible`, поэтому `:focus-visible`
превращался в `-visible` и давал несуществующие селекторы. Альтернативы
сортированы по длине; после исправления число «ненайденных» упало с 1057 до 847.

### Результат

| показатель | значение |
|---|---:|
| CSS-правил в runtime-файлах | 2 920 |
| уникальных нормализованных селекторов | 2 032 |
| встречаются в статическом DOM хотя бы одной страницы | 1 164 |
| сработали в браузере хотя бы раз (80 прогонов) | 1 600 |
| не встречаются в DOM ни на одной странице | 847 |
| из них не сработали ни в одном прогоне | 381 |
| после отбрасывания артефактов нормализации | 378 |
| **их суммарный размер в исходниках** | **53 391 Б из 467 582 Б (11%)** |
| селекторов, не упомянутых **нигде** в репозитории | **0** |

Последняя строка — главная. Каждый «неиспользуемый» селектор где-то упомянут:
в другой странице, в JS, в тесте или в документации. Ни одного забытого блока,
который можно было бы удалить целиком, нет.

### Почему «59% не используется» — не приговор

Число 59% Chrome считает на **одной** странице в **одном** состоянии. Но:

- 466 селекторов, отсутствовавших в статическом DOM, **сработали** в браузере,
  как только появились интеракции. Это состояния, а не мёртвый код.
- `.cart-drawer.open`, `.hero-title-seo .w` — примеры ложных кандидатов: в момент
  моей проверки они не появлялись, хотя правила существуют.
- 169 классов, не нужных главной, нужны другим страницам (`bottom-nav`,
  `bridal-route`, `calc-*`, `city-delivery`).

Наивная чистка «того, что не на главной», снесла бы калькулятор, нижнюю
навигацию и свадебные блоки на 16 страницах. Выигрыш (11% файла, из них в gzip
ещё меньше) не оправдывает этого риска, поэтому **чистка CSS не делалась**.

## Часть 2. Что на самом деле стоило 1432 мс

### Наблюдение

Трассировка загрузки `/` (CPU ×4, как в CI) показала не один большой пересчёт, а
**непрерывную работу**: после первой секунды пересчёт стилей шёл ~60 раз в
секунду все пять секунд замера.

```
секунда от старта | Layout мс (событий) | Style мс (событий)
       0          |      553 (8)        |      152 (10)
       1          |       24 (3)        |      105 (43)
       2          |        0 (0)        |      162 (59)
       3          |       47 (45)       |      122 (60)
       4          |       33 (25)       |      116 (60)
       5          |        0 (0)        |      107 (56)
```

Две анимации давали эту нагрузку:

**1. `titleShimmer` анимировала `left`.** Блик по заголовку секции:
`animation: titleShimmer 8s ease-in-out infinite`, ключевые кадры двигали
`left: -80% → 120%`. `left` — свойство раскладки: каждый кадр браузер обязан
пересчитать геометрию. Пять заголовков на главной, бесконечно.

**2. `shimmer` у скелетонов анимировала фон, которого нет.** Правила
`.skeleton-img` и `.skeleton-line` объявляли градиент и
`animation: shimmer 1.4s infinite linear` (`background-position`). Но ниже по
каскаду стоит `.skeleton-img,.skeleton-line{background: var(--cream-dark)}` —
тот же селектор, тот же вес, позже в файле. Он затирает градиент, поэтому
анимация двигала `background-position` у элемента с `background-image: none`.
Проверено в браузере: `background-image: none`, `background-size: auto`,
`animation-name: shimmer`. Ноль визуального эффекта, полная стоимость пересчёта.

### Исправление

- `@keyframes titleShimmer` переведены с `left` на `transform: translateX()`.
  `left:-80%` остаётся в базовом правиле (это же состояние покоя для
  `prefers-reduced-motion`), анимация добавляет `translateX` поверх. Пересчёт
  эквивалентности: конец хода `left: 120%` = `-80% + 200%` контейнера; ширина
  элемента 40% контейнера, значит `200% / 40% = 500%` собственной ширины.
- У `.skeleton-img` и `.skeleton-line` убрана `animation: shimmer` — она не
  влияла ни на один пиксель (см. выше), видимая волна остаётся у
  `::after`-оверлея с `skeletonShimmer`, который анимирует `transform`.

### Измерено

Трассировка, CPU ×4, стенд `scripts/serve_pages_artifact.py` (как в CI),
3 прогона вперемешку, медиана:

| | до | после | разница |
|---|---:|---:|---:|
| пересчёт стилей | 785 мс (292 события) | **321 мс (94)** | −464 мс, событий в 3.1× меньше |
| раскладка | 706 мс (86 событий) | **623 мс (11)** | −83 мс, событий в 7.8× меньше |
| **Style & Layout** | **1 491 мс** | **939 мс** | **−552 мс (−37%)** |

Симулированная модель Lighthouse (настройки CI), 6 пар вперемешку:

| | до | после | парная медиана |
|---|---:|---:|---:|
| Style & Layout | 1 132 мс | 953 мс | **−194 мс** |
| LCP | 2 654 мс | 2 671 мс | **−9 мс** |
| TBT | 136 мс | 103 мс | −55 мс |

### Чего это НЕ даёт

**LCP не улучшился.** Парная медиана −9 мс при разбросе ±650 между парами — это
шум, а не эффект. Один прогон дал −647 мс, другой +682 мс; принимать любой из них
за результат было бы ровно той ошибкой, из-за которой появился этот документ.
Причина понятна: анимации работают и после LCP, а сам LCP определяется доставкой
hero-картинки, а не пересчётом стилей.

Порог 2500 не трогался. Бюджет LCP этой правкой **не закрывается**.

Что правка даёт по факту: втрое меньше пересчётов стилей и в восемь раз меньше
раскладок на каждой загрузке главной — это плавность прокрутки, расход батареи
на мобильных и запас по main-thread, но не место в шкале LCP.

## Проверка внешнего вида

Правка не должна менять картинку, поэтому она проверялась попиксельно, а не
«на глаз». Кадры анимации фиксировались через Web Animations API
(`animation.pause(); animation.currentTime = ms`) — иначе сравнение ловит разную
фазу, а не разницу.

| кадр | изменённых пикселей | макс. дельта канала |
|---|---:|---:|
| 0 мс | 1 141 из 132 888 (0.86%) | **1 из 255** |
| 200 мс | 1 145 из 132 888 (0.86%) | **1 из 255** |
| 400 / 700 / 900 / 1120 / 1400 / 3000 мс | 0 | 0 |

Единица в младшем разряде канала — разница путей интерполяции (`left` против
`transform`), ниже порога восприятия и ниже любого реального отличия.

Скелетоны: 907 изменённых пикселей из 112 520, макс. дельта **1** — это фаза
`skeletonShimmer`-оверлея в момент снимка, а не следствие правки; удалённая
анимация не имела видимого выхода вовсе.

## Как повторить

```bash
# 1. база: отдельный worktree на нужном коммите (git archive не годится —
#    .gitattributes кладёт scripts/ и tests/ в export-ignore)
git worktree add /tmp/base-site <sha>
cd /tmp/base-site && python3 scripts/build_pages_artifact.py

# 2. два стенда
python3 scripts/serve_pages_artifact.py --port 4403 --root /tmp/base-site/_site &
python3 scripts/serve_pages_artifact.py --port 4402 --root _site &

# 3. трассировка: сумма UpdateLayoutTree и Layout при CPU ×4
#    (Emulation.setCPUThrottlingRate), по 3 прогона вперемешку
```

Важно: не пересобирать `_site` между сравнениями. В первый раз я пересобрал
артефакт в том же каталоге, который отдавал «базовый» стенд, и сравнение
показало отсутствие разницы — потому что оба стенда отдавали уже исправленный
файл.

## Что осталось незакрытым

- **LCP 2500 по-прежнему не достигнут.** Локально симуляция даёт 2654–2671 мс при
  бюджете 2500. Рычаг — доставка и декодирование hero-картинки, не CSS.
- **Первая секунда: 553 мс раскладки на 8 полных пересчётов документа.** Это
  отдельная задача (объём DOM 1 909 объектов в момент первой раскладки), её эта
  правка не касается.
- 378 правил-кандидатов (53 КБ, 11%) не удалены осознанно: нулевой селектор не
  подтвердился как мёртвый, а риск для 16 страниц выше выигрыша.
